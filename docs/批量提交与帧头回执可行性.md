# 批量提交与帧头回执可行性（2026-10-18）

结论：**已经确定的多批工作可以连续提前录制，CPU可以在后续帧头集中消费已到达的回执；不能保证提交后的下一帧就收到全部回执，也不能因此消除所有同步依赖。** 当前三槽位把结果消费和资源复用绑在一起，仅改变回执处理时机不足以打通第四批。

本次只增加隔离验证工具和分析记录，没有修改正式Pipeline、Transport、槽位状态机、shader或数值规则。

## 实际验证

[隔离探针](../tools/unified_edit_pipeline/check_submit_ahead.gd) 使用真实主RenderingDevice、现有默认catalog和产品shader，构建256×256的固定沙水域。铲子深度0.15m、槽宽/肩宽0.5m、水策略3、速度参数0.25m/s。它只覆盖回执入口，把回调已经提供的独立字节副本存入CPU收件队列，延后调用原有的校验逻辑。

准备四个有顺序依赖的工作单元：

```text
批1：BEGIN + 铲子段A
批2：水tick
批3：铲子段B + END
批4：水tick
```

一次 `pump()` 后暂停CPU消费，等前三批回调全部到达，再异步读取原始GPU控制缓冲。随后在 `SceneTree.process_frame` 帧头信号中集中消费回执并调用原有pump。

| 观测点 | GPU / CPU状态 | 结论 |
|---|---|---|
| 一次pump之后 | 三个槽在途，第四批仍pending | 当前可以一次录制三批 |
| 三个回调已到，CPU尚未校验和消费 | 原始GPU `state_seq=3, tick=1`；CPU `state_seq=0`，结果表为空 | GPU后续批次不需要CPU批准前批结果 |
| 再延迟两帧消费 | 第四批仍pending | 即使前三批完成，旧租约仍限制提交 |
| 首次帧头集中消费后 | CPU `state_seq=3`；三个槽均为 `CPU_RECLAIM`，第四批仍pending | 把消费移到帧头并不会自动消除退役确认环节 |
| 后续帧头继续处理 | CPU `state_seq=4, tick=2`，四批全部排空 | 可以按“已完成才处理”方式运行；两条铲子命令均有真实APPLIED结果 |

19项检查全部通过，资源正常释放，产品来源哈希运行前后相同。原始证据见[probe.json](../test_output/submit_ahead_feasibility_20261018/probe.json)、[日志](../test_output/submit_ahead_feasibility_20261018/probe.log)和[GPU控制缓冲](../test_output/submit_ahead_feasibility_20261018/probe.control.bin)。本探针用于依赖关系验证，不是主沙滩帧率测试。

交付核对发现测试结束后共享工作区的 `height.gd` 新增了其他工作的 `footprint_ready` 逻辑，本次未改动它。对应测试版本已按原哈希归档到 `verified_sources.zip`，差异记录在同目录 `verification.json`；不将已完成测试冒称为对后续版本的重新验收。

## “下一帧开头”需要区分提交和回执到达

重新分析前次实际主沙滩的CPU时间线，用提交录制结束后的第一个 `process_frame` 采样点定义“第一个后续帧头”。只纳入具有完整前后采样边界的批次：

| 有效原始轨迹 | 批次数 | 第一个后续帧头前已收到 | 最早可在第几个后续帧头消费 |
|---|---:|---:|---:|
| 干区 host | 414 | 0 | 全部为第2个 |
| 浅水区 wet | 424 | 0 | 全部为第2个 |
| 浅水区 wet_water_sparse | 418 | 0 | 全部为第2个 |

原始逐批次时间见[帧边界重分析](../test_output/submit_ahead_feasibility_20261018/frame_boundary_reanalysis.json)。它说明当前这批D3D12实测不能按“帧N提交、帧N+1开头必收齐”设计；不是Godot所有平台固定延迟两帧的保证，也没有把回调时间冒充GPU执行结束时间。

可行的约定应是：**每个帧头只取当时已经到达的回执，未到达的保留到后续帧，主线程继续工作。** 如果为了帧N+1一定拿到结果而等待，反而重新引入阻塞。

## 一次性提交的边界

- 数值层面可提前排队：GPU已经负责候选计算、校验和条件提交；下一批读取前批提交后的GPU状态，不需要CPU重新上传结果。批次仍必须保留原来的编辑/水tick顺序及GPU读写依赖。
- 当前实现的上限是三个在途工作槽，且每个编辑批最多64条命令；编辑批和水tick是不同工作类型。单个“批”不是任意编辑和水tick的无边界混合包。
- 超过三批需要修改在途资源管理，例如提供足够且有界的独立输入/结果存储，或将工作缓冲的最后使用证明与CPU业务回执消费解耦。**本次没有实现或运行验证超过三槽的方案**，不能把三批的验证宣称为无限提交能力。
- 回执已回到CPU后，校验、记账、UI通知可以延后；GPU输出仍在被使用/读取时则不能随意覆盖。结果必须保留到消费，错误回执、代次切换、关闭和恢复也必须保留原有生命周期证明。
- 连续拖动后续的鼠标位置尚未产生，无法整条笔划提前提交；可以一次排入的是当时已确定的工作。

## 能消除和不能消除什么

| 项目 | 可行性 |
|---|---|
| 让CPU不逐批等待结果才能录制下一批 | 在可用资源容量内已验证；更大窗口需调整资源管理 |
| 回执集中到帧头处理 | 已通过隔离验证；只能处理已经到达的数据 |
| 保证所有回执在提交后下一帧开头到齐 | 当前实测不支持 |
| 彻底消除GPU读写依赖和资源生命周期同步 | 不可行，这些是正确性条件 |
| 消除CPU回执校验、记账和碰撞处理成本 | 不能，移动时机不等于取消计算 |
| 消除湿区铲子的27ms GPU热点 | 不能，该计算成本不由回执处理时机决定 |

可研究的后续结构是“帧头取已完成回执 → 处理已具备证明的资源回收 → 将当前已知工作在有界容量内连续提交；未完成的不等”。需要另行验证退役路径、错误处理和渲染预算后才能实施。仅靠积压更多昂贵工作，可能增加输入到显示延迟及渲染等待。
