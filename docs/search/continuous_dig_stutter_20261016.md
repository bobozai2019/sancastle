# 连续挖填低占用卡顿：竞品与Godot分析

2026-10-16。角色：技术分析与待验证假设。本轮只核对源码、既有运行证据、竞品GPU导出及Godot官方实现，不改代码、不重跑GPU负载、不分析竞品业务。用户报告“连续挖卡顿严重、后台CPU/GPU占用不高，竞品占用较高但流畅”；该现象尚未与同输入帧时间、线程和GPU时间线配对。

最值得先查的是**单工作组全域串行计算拖长关键路径，再经渲染队列/飞行帧同步影响画面**。合批已减少往返等待，但没有减少每笔核心计算；总占用率低不能证明关键路径便宜，也不能仅据占用率认定主因已证实。

## 1. 已有事实与未知

| 观察 | 证据与可信边界 |
|---|---|
| 合批处理更快，长帧更差 | 同轮main短测12笔1460.083→763.151ms，最长帧50.000→74.353ms；96项通过，14份双槽字段逐字节一致。是当前短窗口事实，不是长期p99或正式成本PASS |
| GPU提交与CPU收尾确有重叠窗口 | 第一组合批的5对相邻批次，上一批碰撞应用时间均落在下一批提交后、回执前；不等于硬件精确同时计算时长已测得 |
| 挖比填有更多核心派发 | 原始batch metrics中挖23次、填12次沙水派发；另有helper、材料、发布和碰撞。不把dispatch数量直接当毫秒成本 |
| 速度检查仍只用一个工作组 | `water_velocity_prefetch`的64线程分批加载65536格，1024轮中由lane0顺序累加；并不是向整张GPU派发大量独立工作组 |
| 水分量/容量也含全域工作 | `water_packed_cached`只派发一个64线程工作组；需要多个屏障、分量/容量遍历。`water_displace_compensated`还有回退路径，但不能未经计数就认定本次卡在BFS回退 |
| 每批重复分配备份 | 批后端每次新建、复制、释放14张备份纹理，以及4个buffer和uniform sets。按当前格式/256²逻辑大小约3.75MiB纹理payload/批，不等于驱动实际分配或已测耗时 |
| 输入是有界队列 | 普通拖动每移动至少0.025m可生成笔段，队列最多64笔、当前每批最多2笔；新输入可能快于消费，产生拖尾甚至容量拒绝 |

## 2. 为什么占用低也会卡

CPU总占用率会摊到多个逻辑处理器；一条关键线程忙或等待，其他核心空闲，总数字仍可能低。还应区分CPU实际计算、锁/驱动/fence等待和未获调度。

GPU的“有核在执行”“多少SM活跃”“warp占用”“吞吐接近上限”是不同指标。一个长工作组只能利用少量GPU并行资源，却仍可能挡住依赖它的后续工作；多个屏障和单线程累加也会拉长完成时间。[NVIDIA关于SM活跃与占用的说明](https://developer.nvidia.com/blog/measuring-the-gpu-occupancy-of-multi-stream-workloads/)。不能拿整卡占用率代替单核持续时间和队列等待。

监控口径也需对齐：Windows任务管理器可按引擎显示3D/Compute/Copy，进程总GPU列采用最忙引擎的口径，并不是简单平均所有GPU单元。若用户看的是某张3D图，需确认是否覆盖实际计算；不能一概称任务管理器数字错误。[Microsoft口径说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)。当前双方的监控工具、采样周期、VSync、窗口和负载尚未统一。

## 3. 竞品能说明什么

本次核对test41 E863源捕帧、Ground.Paint DXBC及asm的hash与既有manifest一致。该核按单元读写，线程组32×32×1；完整编译核没有loop/endloop、sync、原子归约或共享内存声明。已有取证中的编辑后GPU沙床随后供顶点着色器读取。这支持其Paint核具有大规模逐格并行结构，不能推出整个原作零同步或已测得低延迟。

原作已知还有异步Readback缓存、MeshCollider更新与Job.Complete，另有同步GetData入口；它是否每笔调用、以何种频率更新碰撞，仍未知。原作Paint的高度印章/量字段模板与本项目指定m³、精确守恒水位移、动量审计不是同一个计算任务，不能把原作的简单Paint公式直接替换当前契约。

最有价值的借鉴是“逐格工作交给大量线程；GPU完成态直接用于显示；CPU碰撞代理消费独立缓存”，而不是追求更高占用数字。原作较流畅与该结构之间的因果仍需同条件动态证据。

详细身份、复验、反证和缺失数据见[竞品结构记录](../competitor/GPU编辑计算_项目对照.md#edit-perf-structure-20261016连续挖填的并行结构与未知成本)及[来源索引](../competitor/continuous_edit_comparison_sources_20261016.json)。旧Water.Paint完整导出路径当前缺失，本次没有新提取或重新宣称其数据完整。

## 4. Godot为什么仍可能等待

本轮引擎为`4.7.2.stable.steam.ed1daf0bf`，对应提交`ed1daf0bf001b61586d9930840f2f1394092c079`。官方精确版本源码显示：

- `RenderingDevice`主队列同时请求GRAPHICS与COMPUTE能力；另有传输/呈现处理，不是本项目已经取得独立异步compute队列。主队列上的重计算及资源依赖可能推迟绘制，具体排队占比尚未捕获。
- `_begin_frame()`先调用`_stall_for_frame()`；后者等待帧fence后才能复用该飞行帧资源。因此项目代码不显式调用`sync()`，也不等于渲染循环完全不会等待GPU。
- `call_on_render_thread()`在调用线程已是server_thread时会直接调用Callable，其他情况才入命令队列；该API不保证多一条独立CPU线程。

来源：[RenderingDevice主队列](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_device.cpp#L8391)、[帧开始](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_device.cpp#L8048)、[帧fence](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_device.cpp#L8214)、[渲染线程调用](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_server_default.h#L1216)。本次只在RAM读取源码并核对函数，不替换本地引擎。

项目已经使用异步回读，不能以“把同步GetData换成async”冒充新修复。官方说明`buffer_get_data_async`/`texture_get_data_async`按一定飞行帧延迟返回，数据对应请求时刻；异步不消除传输成本。[RenderingDevice参考](https://docs.godotengine.org/en/stable/classes/class_renderingdevice.html#class-renderingdevice-method-buffer-get-data-async)。其帧延迟不代表本项目应再机械添加同样次数的物理帧等待，也不应照搬local RD教程给全局RD新增`submit/sync`。

## 5. 候选原因与区分方法

| 优先级 | 候选原因 | 现有支持 | 最小区分观测 |
|---|---|---|---|
| 1 | 单工作组/单线程全域水归约拉长GPU关键路径 | 当前选核和派发直接可查；旧测已有重核线索，当前精确占比未知 | 补齐合批GPU阶段时间戳，分别记录水分量、位移、速度审计、沙归约，避免全图逐帧读回 |
| 1 | 重计算挤占渲染队列、帧fence等待 | 引擎队列/帧复用机制与最长帧变差支持；本次尚无完整GPU队列时间线 | 同时记录提交CPU时间、GPU阶段、渲染/Present、帧fence原生等待，区分计算、排队和等待 |
| 2 | 每批14张备份及buffer/set分配、复制和释放带来驱动尖峰 | 当前代码明确每批重建，但未测其独立占比 | 保持算法和输入不变，仅预分配并复用同等容量资源，对照CPU录制和最长帧 |
| 2 | 输入采样速度超过消费，队列拖尾 | 2.5cm笔段阈值、64容量与当前吞吐已知 | 记录事件时间、队列长度/年龄、接纳→发布/碰撞延迟，区分画面长帧与操作积压 |
| 3 | 主线程碰撞准备/形状替换/Jolt同步尖峰 | 碰撞在主线程提交；旧有成本记录，本轮没有独立定位 | 将解码/准备/替换及物理阶段分开计时，核对受影响块数和是否重复更新 |
| 3 | UI采样、字体、资源分配、驱动/系统调度 | 可能贡献尖峰；当前已有显式字体，不能套用旧字体长尾当本次根因 | 卡顿窗口CPU线程栈与小范围采样；一次只隔离一个因素 |

即使每次接收输入的CPU代码很短，队列也可能积压。例如移动1m/s、每2.5cm接一段，理论可达约40段/s；这不是实测输入速率。已测混合挖填约15.7笔/s也不是纯挖稳态吞吐；两者只说明必须量测队列，而不能仅看后台占用率。

## 6. Godot适配建议与实施顺序

1. **先把当前卡顿分段测清楚。** 固定普通连续挖的轨迹、体积、相机和负载，记录帧间隔、输入排队年龄、CPU命令录制/分配、GPU分阶段、碰撞CPU及帧等待；不要先同时改多线程、批大小和水公式。未量测前不承诺哪项占比最高。
2. **先做不改数值的资源复用。** 将14张回退纹理和批缓冲/sets预分配复用，保留真实回退、代际与在途所有权。这能去掉明确的重复分配，是否改善长帧用单变量对照判定；不删除守恒保护。
3. **把GPU单工作组热点改成真正并行。** 单格表达式先在多工作组计算，归约考虑分层/补偿方案；按原守恒、下限和浮点误差预算验收。若要求逐位重现旧顺序累加，只能保留最终有序折叠，收益可能受限，不能默改数值契约。湿分量/容量处理也需独立优化，不能只优化速度核就宣布解决。
4. **研究纯挖快速路径和可证明的缓存复用。** 纯降低沙床没有填高排水需求，有机会避免重复连通/容量求解；速度扰动、干湿限制及必要审计仍要保留。若复用湿拓扑或未改区域统计，必须按真实水/障碍变化失效；暂停和实时状态分别验，不能只用全局revision猜相同。
5. **以帧预算组织计算，再处理输入压缩。** 批大小只是笔数上限，不是GPU毫秒预算；必要时跨帧推进短计算阶段，显示上一份完整完成态，同时限制碰撞CPU每帧峰值。连续轨迹可研究保留路径/长度/总量的重采样，不能随意把弯曲轨迹拉直或合并成一个体积命令；原“多笔只做一次水响应”已有数值失败，不能直接启用。

增加CPU工作线程、调Jolt线程或直接换Vulkan只能作为受控候选；它们不会自动消除单工作组GPU串行计算。独立local RD还涉及纹理共享与同步，当前不为此重构渲染后端。优先目标是稳定帧时间和输入反馈，不是把CPU/GPU占用率数字拉满。
