## GPU 时间

以下使用 04 正常运行拖动，121 笔、61 批。只配对同一捕获帧内时间戳，当前 D3D12 驱动值按 ns 换算。父级/子级跨度相互包含，不能再相加。

| 阶段 | 单次中位 GPU 时间 | 解释 |
|---|---:|---|
| `water_7_0` → `water_packed_cached` | **11.66 ms/笔** | 湿区连通、分量/容量，一个 64 线程工作组 |
| `water_6_0` → `water_velocity_prefetch` | **11.96 ms/笔** | 速度/动量/能量归约，一个 64 线程组，lane 0 顺序折叠 |
| 整笔命令（包含上述两项） | **24.27 ms/笔** | 沙水及 helper |
| 整批 | **48.73 ms/批** | 首批 1 笔、后续 60 批各 2 笔 |
| 14 张纹理备份复制 | 0.173 ms/批 | GPU 复制跨度，CPU 创建/录制另计 |
| 视口绘制 | 18.15 ms/帧 | 不包含前面的外部编辑 compute |

两个水核累计 **2884.17 / 2968.84 ms，占整笔命令 GPU 时间 97.15%**。普通连续挖的主要 GPU 热点已有运行证据，不能仅以派发数量或沙笔刷本体笼统归因。

61/61 个含编辑批次的捕获帧均观察到编辑结束后才进入视口绘制。实例：GPU 捕获帧 **290**、批次 **10**：

```text
GPU：两笔编辑 48.998 ms → 间隙 0.151 ms → 绘制 17.774 ms
     从编辑开始到绘制结束共 66.922 ms
```

全部同帧跨度的中位为 **66.96 ms**。这直接支持“编辑计算后串行绘制”的关键路径归因。尚未取得原生 fence/Present 调用栈，不能把 CPU 帧剩余时间精确标作 fence 等待，也不能把 GPU 帧号直接当作显示帧号。

## CPU 与等待

04 正常运行拖动的调用墙钟中位如下；分配/驱动调用可能含等待，不等于线程实际执行指令时间。

| 阶段 | 中位耗时 |
|---|---:|
| 输入处理（含拾取/接纳） | 0.149 ms/事件 |
| 命令编码 | 0.156 ms/批 |
| GPU 命令录制整段 | **6.268 ms/批** |
| 其中新建并录制 14 张备份复制 | **5.218 ms/批** |
| 回执/账本结算 | 0.222 ms/批 |
| 发布命令录制 | 1.032 ms/批 |
| 批资源释放调用 | 0.356 ms/批 |
| 碰撞解码、准备和形状应用 | **0.688 ms/次**；P95 1.262 ms |

备份逻辑 payload 约 3.75 MiB/批。资源复用值得做，但它不能单独消除每批约 49 ms 的 GPU 水处理。

提交到回执中位 **86.94 ms**，并非纯 GPU 时间，还含排队、飞行帧回收、回读与回调调度；回执到发布确认约 18.39 ms，发布到碰撞应用约 22.91 ms，碰撞应用到控制器确认下一物理边界约 66.44 ms。这些区间可与下一批重叠，不能当作每帧独占负载求和，尤其不能说 Jolt 实际计算了 66 ms。

当前引擎的 `Performance.TIME_PROCESS/TIME_PHYSICS_PROCESS` 每秒以最大值刷新，探针保存原值，但分析排除其逐帧平均/占比解释。见[精确版本 main.cpp](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main.cpp#L5136)。视口统计范围见[RenderingServer 官方说明](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu)。

## 调度与占用率

**常规模拟受到持续编辑的挤压。** 04/05 正常运行拖动的 6 秒窗口内 `completed_ticks` 增量均为 **0**；05 不操作窗口推进 95 tick。队列持续待处理时优先编辑，`_start_tick()` 又受输入和碰撞在途条件限制。“暂停”和“正常运行拖动”成本接近，是这段时间常规 tick 没获得执行机会；编辑自带水位移/速度响应仍执行。

本次 NVML 整卡 GPU busy 多数为 **93–100%**，未复现用户看到的低 GPU 数字；05 拖动进程 CPU 约 **1.4–4.3%**（按 8 逻辑处理器归一）。NVML 是整卡口径，后台编辑器也存在，它不代表本进程独占利用率、SM/warp 占用或吞吐效率，不能据此否定用户观察。仍需对齐任务管理器的引擎图和采样口径。

## 优先级与剩余未知

1. **两个水核优先**：验证纯降低沙床是否可跳过无需求的连通/容量求解，并行化逐格工作与归约，保持守恒、动量/速度审计、回退和误差预算。
2. **复用备份纹理/缓冲**：减少约 5 ms 的重复 CPU 创建/录制成本，保留在途所有权；与 GPU 算法改动分开对照。
3. **按 GPU 时间预算与公平性调度**：当前两笔约 49 ms 已超过 16.67 ms 帧预算；扩大批次会进一步拉长同帧计算。需要给绘制和常规 tick 留执行机会。
4. **再处理输入重采样**：保持轨迹、总量与顺序，减少过密笔段；不重新启用已有数值失败的“多笔只做一次水响应”。

以上优化尚未实施。首秒额外尖峰、原生 fence/Present 精确分解、独占硬件长稳仍未知。没有新的竞品分析，之前竞品结论及旧性能失败保持原判。
