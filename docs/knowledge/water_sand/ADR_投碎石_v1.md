# 投碎石 v1

2026-10-16，按用户要求新增投碎石工具。本项目 Godot 功能，沿用已有纯表现碎石；不增加权威沙量、障碍、排水或刚体碰撞语义。

## 交互和容量

左侧 `gravel_drop` / “投碎石”，每次 1–128 颗，默认 16；半径 0.45 m 圆盘内固定种子均匀散布。左键投放，拖动每移动至少 0.6 m 可追加一批；一批处理期间不累积点击队列。可投在干沙或水中，使用当前碰撞沙床定位；右键转向、松键、改工具/参数和失焦停止拖动。

总容量仍为 1024。`gravel_count` / profile.count 仍表示初始种子颗数，默认 512；新增独立 `active_count`。只有剩余容量足够时整批追加，不覆盖、不回收旧颗粒；容量不足提示可用颗数。新颗粒使用未占用的连续 ID，因此尺寸/输运响应种子和保存恢复稳定。

碎石贴沙床随水搬运的阈值、响应、速度上限和微步规则均沿用原实现。水深和流速不足时停留；暂停不发生水平输运；不是空中下落、逐颗拾取、真实滚动或阻水石块。

## 状态和生命周期

GPU kernel mode 3 追加：旧活动 ID 逐位复制当前状态，只初始化新 ID；新颗粒高度/湿水状态从同 generation、tick、revision 的完成态床/水读取。不写任何权威水沙纹理或账本，也不增加权威 state_revision。

主线程设置 `gravel_drop_pending` 暂停新 tick 入场，等待旧 tick 和沙工具事务结算后在渲染线程投放。成功后发布当前颗粒纹理和活动绘制数量。保存、恢复、场景切换的保存步骤及关闭等待投放结束；场景切换/存档保留各自新增颗数和两个原始颗粒槽。

`visual_extensions.gravel_v1` 保留容器名称，但新记录 version=2，额外记录 `active_count`。count/profile_values 仍是初始配置，校验 `count <= active_count <= capacity=1024`，未活动 ID 的两个槽必须为零。读取 v1 时活动数默认取原 count；不放宽已有引擎、源码和配置身份校验，不承诺跨版本旧存档自动迁移。工具选择内 parameters={count:int}，独立校验 1–128，随切场景沿用。

## 验证

- `tests/integration/gravel_drop_probe.gd`，最终 `test_output/gravel_drop_20261016_v2/result.json`：可见 D3D12 / GTX 1050，三个入口的真实 UI/水下碰撞投放、干地投放、旧颗粒保持、局部范围、实际绘制数量、水沙/动量逐位不变、容量不覆盖、坏坐标/非法活动数拒绝、version 2 保存、恢复双槽及工具选择、场景切回颗粒完全相同、关闭释放。两个 test1 场景观察到新增碎石随水流移动。
- `tests/gravel/gravel_drop_transport_probe.gd`，`test_output/gravel_drop_transport_20261016/result.json`：32² 控制输入、空池追加 16 颗；水深 0.1 m、qx=0.1、响应固定 0.5 时，各颗粒位移等于 0.5/30 m；干地保留 XZ；重新入水、反向 qx 后恢复反向移动。
- `test_output/gravel_drop_smoke_20261016/result.json`：45 项原 UI 显隐/拖动/沙床编辑回归通过。

v1 集成报告保留：main 落点在起始短窗口中没有达到原碎石的输运阈值，“所有场景 20 tick 内必须移动”检查失败；不能据此改变流速或输运系数强迫移动。最终用两个有流场景的实际观察及独立恒定流输入验证新颗粒输运。没有新增完整负载成本、长稳、逐粒碰撞或严格多 tick 恢复继续结论。
