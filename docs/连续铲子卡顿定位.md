# 连续铲子卡顿定位（2026-10-18）

本轮仅增加观测并定位原因，没有修改数值算法、批处理策略、槽位数量或碰撞消费策略。诊断默认关闭。主沙滩浅水区已经复现百毫秒级停顿，主要热点确认在 **铲子附带的 GPU 湿区排水计算 `water_packed_cached.glsl`**。工作槽周转另有稳定的反馈延迟，碰撞更新进一步占用主线程。

## 测试条件和证据

- Godot 4.7.2 steam `ed1daf0bf`，D3D12 Forward+，GTX 1050，i5-9300H，真实可见窗口 1280×720，VSync=1；编辑器保持开启。
- 正式 `scenes/main.tscn` 初始化、默认 `shovel_v1`：深度0.15m、槽宽0.5m、肩宽0.5m、水策略3、速度参数0.25m/s；没有替换产品 shader。
- 自动探针：预热、暂停空闲、水运行空闲、运行中两条80样本笔划、暂停后两条80样本笔划；输入每帧推进、每条3m，末尾正常 drain/release。移动使用真实 PlayerInput 和预览路径；射线拾取另行计时，不决定自动路径。
- 干区初始脚印中心格 `(224,184)`，浅水区 `(64,168)`；浅水脚印初始水深0.0148～0.2898m。都是固定初态上的自动复现，不是用户原鼠标轨迹。后续水与沙随真实执行演化，运行/暂停阶段不是同一状态重放。
- 原始 JSON、日志、分析和 CPU 时间线：[证据目录](../test_output/shovel_latency_20261018/)。每轮保存配置和来源哈希；有效轮次运行期间没有哈希漂移，自动轮次的161项产品配置来源一致。诊断脚本版本和采样模式另行记录。
- 启停附近记录了 Godot 进程；一次间隔检查发现其他任务的瓶子探针，等其结束后才启动下一轮 GPU 采集。没有持续独占GPU监控，不宣称完全排除所有系统背景负载。

## 结论一：湿区铲子在 GPU 上出现大范围排水成本

低干扰 CPU 轨迹 `wet.json` 已复现：运行中连续铲动160帧，帧时间 **P95 135.89ms、最大140.68ms**。暂停水 tick 后继续铲湿沙，P95仍为44.71ms。普通水 tick 不能解释这个数量级。

`wet_water_sparse.json` 使用每帧至多一个水响应的分段采样，227个水响应样本，未超出时间戳容量：

| GPU 阶段 | 中位数 | P95 | 证据意义 |
|---|---:|---:|---|
| 铲子水响应整体（不含独立 commit） | 28.34ms | 28.70ms | 每个被采样的编辑命令 |
| `packed` 湿区处理 | **27.27ms** | **27.62ms** | 占水响应约96%，主要热点 |
| `velocity_reduce` | 0.734ms | 0.756ms | 次要固定成本 |
| 名为 `displace` 的后续兼容 dispatch | 0.007ms | 0.008ms | 本路径的主要排水已经在 packed 内执行 |
| 普通水模拟 tick | 1.308ms | 1.458ms | 不是这次严重停顿的主要计算段 |
| 完整编辑批次，水运行中 | 30.17ms | **118.55ms** | 一批可能包含多条命令，不能当成单命令成本 |

同轮帧时间P95为137.23ms。65个运行中编辑批次里，34批含1条命令、30批含4条、1批含7条；控制命令和无变化命令不等价于完整排水命令。多个昂贵编辑合在一批，形成百毫秒级 GPU 工作，与实际慢帧量级一致。

代码证据：

- [水响应入口](../scripts/simulation/unified_edit/water_response.gd) 顺序执行 prepare → packed → displace → velocity → velocity_reduce → audit；commit另行执行。
- [packed shader](../shaders/simulation/edit_validation/water_packed_cached.glsl) 只有一个64线程工作组；先扫描256×256域、建立湿区连通结构。`has_demand==0` 在结构构建后才退出。
- 存在抬床排水需求时，按湿区连通分量多次遍历 `wet_count`，有大量工作组 barrier 和 `lane==0` 的64项串行累计，还要做容量、分配、残差修复和守恒审计。局部铲子可以触发很大的水域处理范围。
- `wet.json` 和稀疏采样轮次保留的末尾真实回执中，单命令 `changed_cells` 约4万，且有非零 `displaced_water_m3`，支持范围确实扩展到大连通水域。该字段涵盖水/动量等变化，**不是铲子改了4万个沙格**。完整332个命令结果的轻量轨迹为320 APPLIED、12 NO_CHANGE，没有业务拒绝。

可信度：**C3** 确认 packed 的时间及完整批次长耗时；**C2** 支持“大湿区多遍扫描、串行累计是增长原因”。没有在 shader 内继续拆分每个循环，不能给出各内部循环的精确占比。

## 结论二：三槽位周转造成反馈延迟，并促使命令合批

干区低干扰 `host.json` 的运行中拖动：

| CPU/调度阶段 | 中位数 | P95 |
|---|---:|---:|
| 输入入队 → 开始录制 | **22.02ms** | 37.88ms |
| 录制结束 → 异步回调进入 | 27.53ms | 29.90ms |
| 回调进入 → 工作槽 FREE | **5.64ms** | 11.24ms |
| 槽 FREE → 下一次获得该槽 | **13.88ms** | 20.14ms |
| 输入入队 → 主线程结算 | 53.75ms | 72.41ms |

这些分位数来自不同样本，不能相加成某一条命令的精确生命周期。`录制结束→回调` 包含GPU排队/计算、传输和引擎回调派发，不能称为纯GPU耗时。

160次运行中调度有159次因无空槽退出，快照始终是两个 `GPU_QUEUED`、一个 `CPU_RECLAIM`。`_poll()` 已消费回执，但 `_retired()` 的 deferred 确认尚未将槽设为 FREE，当前 pump 就先遇到 no_slot；之后还要等下一次 pump 才获得该槽。这个依赖已由同批次事件直接测到（C3）。

暂停水 tick 的干区拖动没有槽位阻塞，入队到录制中位数降至1.73ms。运行中水 tick 和编辑共享三槽位，干区每帧输入最终常合成每批约2条编辑。浅水区GPU长批次又增加回执延迟，进一步改变合批节奏。

注意：本机记录到 submit、回调、receive、consume、retire 的线程ID均为1。`call_on_render_thread` 是执行上下文接口，不能据函数名推断本次存在一条独立于主线程并行运行的 GDScript 录制线程。GPU仍是异步设备执行。

本轮没有测到“后批已完成但被先批挡住”的乱序回执队头阻塞。也没有GPU绝对时间与CPU时钟校准，**不据这组数据宣称 GPU 空转了多少毫秒**。

## 结论三：碰撞写入是额外的主线程尖峰

干区 `host.json` 最慢35.65ms帧里，实际 `HeightMapShape3D` 替换占5.79ms，完整高度消费占6.09ms；同一帧回执校验占4.04ms。另一个31.21ms帧的录制调用占9.29ms。它们直接占用主线程，不能把这类尖峰都归给GPU。

碰撞worker只做数据准备：干区运行中worker中位数0.61ms、P95 1.81ms；真正形状修改仍由物理主线程集中执行。worker结束到物理消费还会有调度等待。

暂缓高度消费的 `height_held.json` 对照中，运行拖动P95从22.68ms变为20.76ms，但槽位阻塞仍159/160，入队等待仍约22ms。这支持碰撞是额外压力、不能单独解释排队。该开关也会使两条高度通道回压，抑制后续捕获/worker；不是纯形状赋值消融，也不将两次P95之差当作精确优化收益。

严重浅水停顿帧达140ms，而相应碰撞只占数毫秒；本轮首要热点已收敛到GPU packed排水，碰撞属于次要叠加因素。

## 本轮未支持的嫌疑和剩余边界

- 干区输入 move P95 0.74ms、射线拾取0.09ms、预览提交0.25ms；没有输入拒绝，pending峰值仅4，没有队列满或结果容量耗尽。
- 未出现worker未完成就阻塞join、生命周期故障、坏回执或资源释放失败。
- 预览提交计时不等于完整预览GPU成本；没有逐项归因引擎渲染、驱动等待、操作系统调度和物理引擎内部工作。因此不把所有帧时间都归到已埋点段。
- 湿区内部各循环耗时、不同水域大小/铲子尺寸的成本曲线，以及用户实际操作轨迹仍未单独验证。已定位到具体慢kernel和调度环节，修复留待下一轮。

## 调试入口

新增 [diagnostics.gd](../scripts/simulation/unified_edit/diagnostics.gd) 为可选有界事件收集器，最多20万事件，溢出计数；主流程默认 `null`。仅诊断启动器挂接。CPU事件关联 command_id、batch_seq、slot、height snapshot，导出回执、槽位、高度worker和实际形状调用。GPU计时与CPU时钟分开，普通运行不启用GPU时间戳。

在仓库根目录运行，输出目录自动按时间新建：

```powershell
# 实际手动操作主沙滩，水默认运行；30秒后自动排空、保存并退出。
# 感觉卡顿时按 F8 留标记；按下后下一次主线程执行时才记录。
python tools/unified_edit_pipeline/run_shovel_trace.py --manual --duration 30

# 自动复现浅水区，先只计CPU生命周期与帧间隔。
python tools/unified_edit_pipeline/run_shovel_trace.py --wet

# 每帧首个水响应做稀疏GPU细分，其余命令仍正常执行。
python tools/unified_edit_pipeline/run_shovel_trace.py --wet --water-only

# 只增加整个编辑批次/水tick计时；省略 --wet 即干区。
python tools/unified_edit_pipeline/run_shovel_trace.py --sampling
```

每次输出 `capture.json` 原始记录、`capture.log` 引擎日志、`capture.analysis.json` 统计，以及可导入 Perfetto/Chrome Trace 的 `capture.trace.json` CPU时间线。`--output` 可指定一个不存在的文件；启动器拒绝覆盖旧证据。`--godot` 可指定其他可执行文件。

分析器 [analyze_shovel_latency.py](../tools/unified_edit_pipeline/analyze_shovel_latency.py) 可以重新分析原始JSON。碰撞耗时按真正的 `[上次process_frame时间,本次时间]` 求交，不按引擎帧号简单拼接。`Performance.TIME_PROCESS/TIME_PHYSICS_PROCESS` 是周期更新的监视值，不用于单帧归因。阶段边界按采样帧归类，边缘命令可能跨一个采样间隔。
