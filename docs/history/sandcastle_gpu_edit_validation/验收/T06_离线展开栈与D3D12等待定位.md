## 已观察事实

新增 `tools/unwind_native_dump.py` 用本机AMD64 DbgHelp StackWalk64离线展开，不打开任何进程。读数来自dump已捕获栈、匹配PE的code/pdata/xdata；模块TimeDateStamp/SizeOfImage/CheckSum核对，Godot另外核对run manifest的完整SHA256。结构布局以本机Windows SDK10.0.26100.0的DbgHelp.h核对，遵循[StackWalk64](https://learn.microsoft.com/en-us/windows/win32/api/dbghelp/nf-dbghelp-stackwalk64)回调约定。所有调用串行，不构造缺失内存、不从任意映射栈词猜返回地址。

TID15016成功14层，到kernel32/ntdll线程启动尾部；没有内存读取失败。主要Godot调用点按外层到等待端：`0x5dba2 → 0x3384c2e → 0x32ec0a7 → 0x32eb4f5 → 0x138c64b → KERNELBASE → ntdll`。PE实际没有Debug Directory、COFF符号表或可用PDB；不能以最近远距离导出当私有函数名。

用官方[Capstone5.0.9 Windows wheel](https://pypi.org/project/capstone/5.0.9/)只反汇编栈中Godot函数范围和一处明确返回链目标。wheel原包SHA256 `732cedbbb56d42e723f14d7af6387f1454194a820b4b96b56d1e53f865ef85d0`核对后解到独立evidence工具目录，未安装全局Python包。原包与LICENSE保留。

`verify_native_unwind.py`独立核对10个Godot返回点确实结束于call指令，直接目标与callee函数范围一致或有经过核验的平衡栈尾调用。首版有一项FAIL：CRT引导call目标0x65ed830的18字节函数恢复rsp后jmp0x52b50，未保留额外栈帧；已补精确指令核验，首版FAIL文件保留。最终10个调用点PASS。两个派生dump负例PASS：Godot模块时间戳不匹配时只展开前2层并拒绝该模块；捕获栈截断至16字节时展开1层后因缺失内存停止。原dump未改动。
