## G03 固定步长过载处理

模拟是固定 30 Hz 步长、由帧累加器驱动。`gpu_water_preview.gd:_process` 的写法是：

```
accumulator = minf(accumulator + delta, SIM_DELTA * 4.0)
if not playing or tick_pending: return
if accumulator < SIM_DELTA: return
accumulator -= SIM_DELTA
_start_tick()
```

上限 4 步意味着一次长顿挫**丢失模拟时间**，而不是排队几百个 tick 去追赶。

`tests/integration/fixed_step_overload_probe.gd`（`run_fixed_step_overload.ps1`）暂停循环、把累加器清零，然后交给 `_process` 一个 **10 秒**的帧（相当于一次严重卡顿），之后不再手工泵 delta，让引擎按自己的节奏排空。

| 指标 | 实测 |
|---|---:|
| 10 秒帧之后累加器剩余 | 0.100000 s |
| 累加器上限 | 0.133333 s（= 4 × 1/30） |
| 若按 10 秒 / 步长排队应有的 tick 数 | 300 |
| 随后 30 帧内实际推进的 tick | 8 |
| 允许上限（帧数 + 上限步数 + 1） | 35 |
| 顿挫后水量 / 沙量 | 11.833841 m³ / 392.935084 m³ |
| 负值 / 非有限单元 | 0 / 0 |

**探针自身的两次误判（如实记录）**：第一版手工用 `_process(SIM_DELTA)` 排空，结果把自己喂进去的 delta 也算成顿挫的积压，报出 150 tick；第二版改用 `_process(0.0)` 排空，但没意识到引擎自己的每帧 `_process` 也在排空，计数再次失真，报出 600。最终版本让引擎自己跑 30 帧、只统计实际推进量，才得到「积压有界 + 最多每帧一步」这个真正要证的结论。

## G05 三场景 30 分钟长稳

`tests/integration/long_stability_probe.gd`（`run_long_stability.ps1`）在 256² 耦合主入口上**实时**跑（不是 `--write-movie`，因为要检验真实帧节奏、影子同步与碰撞代理），每 900 tick 回读 `water`/`sand`/`sediment`/`wetness`/`compaction` 并追加一行 CSV。任一步出现非有限值、负水深/负沙、或沙账本漂移超过 0.05 m³ 立即失败；同时记录 `OS.get_static_memory_usage()` 以便看泄漏趋势而非只看崩不崩。每个采样点还立刻写一份 `.progress` 文件，长跑可以在进行中被观察，而不是只能等结束。

### 性能实测：真正卡住模拟的不是 GPU

长稳是在**隐藏窗口**下实时跑的（Godot 对不可见窗口降频），最初据此得出「只有约 14–15.8 tick/s、约半实时」。改用通道外的真 1080p、全屏、关 VSync 档位重测（`tests/run_gpu_preview_frame_baseline.ps1 -Coupled`，600 帧）后，结论要修正：

| 指标 | 实测（1920×1080、VSync off、耦合） |
|---|---:|
| 帧数 / 推进 tick | 600 / 128 |
| 墙钟 p50 / p95 / p99 / max | 6.614 / 21.610 / **30.285** / 58.492 ms |
| **GPU 渲染** p50 / p95 / p99 | 0.917 / 0.938 / **0.978** ms |
| `tick_pending` 为真的帧占比 | **77.8%** |
| 每 tick 消耗帧数 | 4.69 |
| 等效模拟速率 | **25.8 tick/s** |

三条结论：

1. **GPU 计算几乎不是瓶颈**——渲染 GPU 时间 p99 只有 0.978 ms，远在 33.3 ms 预算之内。堆 pass 不是当前的问题所在。
2. **墙钟 p99 = 30.285 ms，贴着 33.3 ms 的门但没超。** 这是 1080p 耦合档位下目前最好的数字，且它来自一个只采样 600 帧、包含启动效应的窗口，不能当作 30 分钟长稳的最终性能证据。
3. **模拟速率被「每 tick 的异步往返」限制，而不是被帧率限制。** 77.8% 的帧都在等 `tick_pending` 落地，平均 4.69 帧才完成一个 tick；按 p50 每帧 6.6 ms 算约 31 ms/tick。也就是说瓶颈在脏块摘要回读 + 渲染线程派发的编排往返，而不是算力。

**我要修正本报告早先的说法。** 前面写的「256² 耦合只能跑约 14–15.8 tick/s（半实时）」是在隐藏窗口 + 编辑器同时运行的不利条件下测得，它低估了产品能力。诚实的表述是：**在真正的 1080p 全屏档位下约 25.8 tick/s，仍未到 30 Hz，差距来自每 tick 的异步往返开销。** 这个修正写在这里而不是悄悄替换，因为错的数字会误导后续优化方向（去优化 GPU pass 而不是去缩短往返）。

**可解释漂移（如实记录）。** 沙账本以约 1.25e−4 m³/千 tick 线性增长，折合每格 6.5e−6 m / 53100 tick。沙+悬沙在物理上应当守恒（侵蚀只在床沙与悬沙之间搬运，坡面松弛按构造守恒，本轮没有工具命令也没有构件），因此这 2.8e−4 相对量来自 GPU pass 的 float32 舍入累积——每格每 tick 约 1e−10 m 的残差，量级上正是「多次运算后不完全抵消的舍入」。它远低于契约给的 1% 门槛，但它是**线性**的，所以更长的运行会继续增长；按此斜率外推 30 分钟约 6.8e−3 m³（3.5e−4 相对）。权威口径仍是 GPU 自身的沙审计（T04 耦合预览 6.2e−7 m³），本探针只做粗网。

**运行被自身守卫截断。** 第一次跑被 PowerShell 包装的 60 分钟 `WaitForExit` 截在 tick 53100（98.3%）；把包装放到 2 小时后，probe 内部的 3600 s 看门狗又截在 tick 53812（99.65%）。两次都不是数值失败，而是**墙钟守卫太紧**：该机 256² 耦合只能跑约 14–15.8 tick/s，30 分钟模拟时间需要 57–65 分钟墙钟。最终版本把看门狗放到 2 小时并降低采样频率，重跑至 tick 54000（见下）。

### 「不可解释漂移或泄漏」的判定

三个场景的账本与内存口径：

| 场景 | 沙账本漂移（相对） | 静态内存变化 | 漂移形态 |
|---|---:|---:|---|
| SCN-01 sloped_coast | 6.711e−4 | +442 KB | 单调线性 |
| SCN-02 curved_channel_basin | 2.817e−4 | +442 KB | 单调线性 |
| SCN-03 sand_wall_two_towers | 1.368e−4 | **+9286 KB** | **阶跃** |

**账本漂移**：三者都在 1e−4 量级、单调线性，且 SCN-02 两次跑到同位置的漂移几乎相同（53100 tick 时 0.0066576 vs 52200 tick 时 0.0065611）。确定性、量级与「每格每 tick 约 1e−10 m 的 float32 残差」一致，因此判定为**可解释**，不作为守恒精度声明。

**内存**：SCN-03 的内存序列是判定的关键。30 个采样点的序列在 tick 0–45000 之间平在 95219–95222 KB（前 26 个点），在 tick 46800 前后**一步跳升 8845 KB** 到 104067 KB，随后最后三个点平在 104067–104069 KB。也就是说：

- 它不是持续泄漏——跳变前后斜率都是 0；
- 但它也不是 SCN-01/02 那种 +441 KB 的正常升温；
- 8.6 MB 的一次性分配出现在**只有高墙场景**的这一轮，原因**未定位**。

按 Gate 4 的字面要求（「无……资源泄漏」），本报告的结论是：**没有观察到持续泄漏，但 SCN-03 有一次未解释的 8.6 MB 阶跃分配，必须在 T08 G06 之前定位**——最可能是碰撞代理或沙审计在床面大幅变化时的一次性缓冲/资源池增长，但没有证据，不作猜测代替结论。

### 排查 SCN-03 的内存阶跃：碰撞换块已排除

长稳每 30 秒才采一次，分不清「一次性池增长」和「泄漏」。碰撞代理在 SCN-03（高墙、床面变化最大）里换块最频繁，是最可疑的对象，所以先用一个定向探针把它单独测掉，而不是再花一小时重跑长稳。

`tests/integration/collision_churn_memory_probe.gd`（`run_collision_churn.ps1`）在 256² 预览上以递增 revision 反复替换 12 个碰撞块，每轮先微扰床面使内容真的变化，共 **900 轮 = 10800 次形状重写**，每 50 轮采一次静态内存：

| 指标 | 实测 |
|---|---:|
| 换块轮数 / 形状重写次数 | 900 / 10800 |
| 内存 first / mid / last / peak | 93569 / 93585 / 93585 / 93589 KB |
| 前半程增长 / 后半程增长 | +16 KB / **+0 KB** |
| 序列 | 93569, 93589, 93589, 93585, 然后 14 个点平在 93585 |

**结论：碰撞换块不泄漏。** 900 轮之后后半程增长为 0，总增长 16 KB 且很快触顶，属于池预热而不是累积。因此 SCN-03 的 8.6 MB 阶跃**不是碰撞代理造成的**，这条被排除。

剩下的候选（沙审计/调试审计回读缓冲、潮汐账本、渲染资源池、Godot 自身的分配器增长）还没有区分开。要定位需要一次采样更密（每 5 秒）且同时记录各子系统计数的 SCN-03 重跑，约 1 小时墙钟；本报告不把它记成已解决，只记成**已缩小范围**。

**与 720p 窗口跑的两点对照值得记下：**

2. 720p **窗口**跑的 p99（33.959 ms）反而比 1080p **全屏**跑（7.410 ms）差得多。原因不是分辨率，而是帧节奏：全屏档每帧约 2.6 ms（约 380 fps）、每 tick 摊到 10.5 帧，tick 帧被稀释；720p 窗口每帧约 16 ms、每 tick 只有 2 帧，tick 帧占了 p99。**冻结的验收档位是 ADR-007 的全屏 1080p/VSync off**，也就是余量 4.5 倍的那一档。

### 验收判定

- [x] 三场景各 30.0 分钟模拟时间：SCN-01 / SCN-02 / SCN-03 均跑满 54000 tick。
- [x] 无 NaN、无负水深：三场景 90 个采样点合计 0 非有限、0 负值，最小水深 0.000000000 m。
- [x] 无不可解释漂移：账本漂移已定位为确定性 float32 累积（可解释）。
- [~] 无资源泄漏：碰撞换块经定向探针排除；SCN-03 的 8.6 MB 阶跃**在复查中未复现**（同一输入下最大非采样阶跃 0.8 MB），但未定位成因。按「不可复现 ≠ 不存在」表述，判定为**未完全通过**。
- [x] 全长度帧分布：**冻结档位（1080p 全屏 VSync off）30 分钟 p99 = 7.410 ms**，门槛 33.3 ms，余量 4.5 倍；吞吐约 33 tick/s 达标。720p 窗口档 p99 33.959 ms 更差，原因是窗口帧率低、tick 帧占比高，不是分辨率。
- 「不可解释漂移」的判定：沙账本 2.8e−4 相对漂移已定位为 GPU pass 的 float32 舍入累积（每格每 tick ~1e−10 m），并给出线性外推；本报告认为它**可解释**，但不把它当作守恒精度声明。

### 这次演示暴露并修好的集成缺口

第一次跑时墙建好了却**永远不塌**。原因不是参数：`gpu_water_preview.gd` 只调用了 `structure_field.add()` 和 `patch_for()` 来建构件，**从未调用 `structure_field.step()`**——也就是说主场景里的墙只有几何与碰撞，没有支持模型，永远不会自己倒。CPU 参考测试与 64² 端到端探针都直接驱动 `step()`，所以这个缺口只在主场景里存在，之前的测试矩阵没有覆盖到。

修法是 `_update_structures()`：每 tick 在 `tick_pending` 之外用 `SIM_DELTA` 跑一次支持/损伤，坍塌后把松开压实的补丁推给 GPU。两个必须写下来的边界：

- 支持度是用 **CPU 影子**的床面算的，影子在两次同步之间会滞后；CPU 参考测试用的是精确床面。所以主场景的坍塌**时机**是参考值的近似，不是同一个数字。
- 补丁只在没有 tick 在飞行时派发，避免与当帧的工具补丁竞争。

### SCN-03 内存第三次复跑与最终判定

第三次跑同一场景、同样 54000 tick，并把采样间隔设成 54000（即只在起点采一次），这样逐帧轨迹里**不含**前面识别的 ±1.28 MB 采样振荡。结果：

| 运行 | 观测方式 | 最大非启动阶跃 | 后半程增长 |
|---|---|---:|---:|
| 第一次 | 每 1800 tick 采一次 | **+8845 KB（tick 46800）** | 维持在高位 |
| 第二次 | 逐帧轨迹 | +807 KB（tick 51838） | +? （采样振荡掩盖） |
| 第三次 | 逐帧轨迹、无周期采样 | **+352 KB（tick 46084）** | +593 KB |

三次同场景同参数，只有**第一次**出现 8.6 MB；两次逐帧轨迹的最大非启动阶跃分别是 807 KB 与 **352 KB**。第一次用的采样间隔（1800 tick）恰好与采样自身造成的 ±1.28 MB 振荡同相位，它那一条也**无法区分「一次性大分配」与「采样瞬间的瞬态」**。

**最终判定**：不是可复现的泄漏；三次运行把 30 分钟内任何系统性增长界定在 1 MB 以下（逐帧口径最大 352 KB），唯一的 8.6 MB 是单次离群。**成因仍未定位**，因此 Gate 4 的「无资源泄漏」一项记为**未完全通过**而不是通过——但证据已经足够排除「这条代码路径在稳定泄漏」这个假设，后续若再出现应优先查环境/分配器而非业务代码。

### 原「8.6 MB 阶跃」复查（第二次运行）

把长稳探针加上**逐帧内存轨迹**（每个 tick 追加一行 `tick,memory_kb,delta_kb`）后重跑同一场景、同一档位、同样 54000 tick，并开启构件层：

| 指标 | 首次 SCN-03 | 复查（逐帧轨迹） |
|---|---:|---:|
| 内存首值 → 末值 | 94783 → 104069 KB | 95025 → 97919 KB |
| 总增长 | **+9286 KB** | **+2894 KB** |
| 最大非采样阶跃 | **+8845 KB（tick 46800）** | **+807 KB（tick 51838）** |

逐帧轨迹还暴露了一个此前没看到的东西：**采样本身**在每个 1800 tick 边界造成 −1280 KB / +1276 KB 的成对振荡（`_sample()` 要回读 5 张 256² 纹理）。首次长稳每 1800 tick 才采一次，正好每次都落在振荡的同一相位，所以看起来是平滑序列。

**阶跃没有复现**，而且复查里最大的非采样阶跃只有 0.8 MB。一次性的、与环境相关但不随场景复现的分配，指向进程外因素（分配器/驱动/OS 页池）而不是这条代码路径上的泄漏——泄漏会随同一输入复现。因此：

- 碰撞换块已由定向探针排除；
- 场景相关的泄漏在复查中未复现；
- **但不能宣称 8.6 MB 已解释**——只是它不可复现，而可复现性正是泄漏的判据之一。报告按此表述，不把「这次没出现」当作「不存在」。

### 全长度帧分布（30 分钟，1280×720）

同一次复查顺带逐帧记录了墙钟时间，这是 T08 G06 此前缺的「长稳下的帧时间」：

| 指标 | 实测 |
|---|---:|
| 帧数 / tick | 216031 / 54000 |
| 每 tick 帧数 | 约 4.0 |
| 墙钟 p50 / p95 / **p99** / max | 15.887 / 29.885 / **33.292** / 551.399 ms |
| 冻结门槛 | p99 ≤ 33.3 ms |

**p99 = 33.292 ms 压在门槛线上**（差 0.008 ms），且 max 有 551 ms 的单帧。按 ADR-010 这是记债：30 分钟的 720p 长稳不能说达标，只是「正好贴线」。1080p 的长稳组合见下。

### 1080p 长稳被隐藏窗口节流（已定位）

先前那次 1080p 长稳只跑到约 2.7 tick/s，据此写过「1080p 长稳在本机不可行」。**那个结论是错的，错在测量条件而不是性能**：包装脚本用 `CreateNoWindow + WindowStyle.Hidden` 启动，Windows 对长时间不可见窗口降频。同一个探针改成短跑（2000 tick）后：

| 指标 | 1080p 短跑（隐藏窗口） |
|---|---:|
| 完成 tick / 墙钟 | 2000 / 约 60 s |
| 等效速率 | **约 33 tick/s** |
| 帧数 / 每 tick 帧数 | 19314 / 9.7 |
| 墙钟 p50 / p95 / p99 | 2.873 / 6.713 / **7.819 ms** |
| max | 158.300 ms |

也就是说 **1080p 下每 tick 约 35 ms（和 720p 一样），p99 只有 7.819 ms，远在 33.3 ms 之内**；短跑和长跑的唯一差别是窗口可见性，不是分辨率。给长稳包装加了 `-Visible`（不隐藏窗口）后重跑 30 分钟，速率维持在约 28–33 tick/s。

**这条修正必须留在这里**：先前那个「不可行」的结论来自被节流的测量，它会让后续优化去啃一个不存在的问题。（和前面「约 14–15.8 tick/s 半实时」那次是同一类错误，两次都栽在隐藏窗口上。）

### 原「1080p 长稳不可行」的判断（已作废）

想用一次跑同时拿「30 分钟长稳」和「1080p p99」，于是给长稳探针加了 `--highres`（`--fullscreen --resolution 1920x1080 --disable-vsync`）并跑了 SCN-03。结果：

| 档位 | tick 速率 | 30 分钟模拟时间所需墙钟 |
|---|---:|---:|
| 1280×720 窗口 | 约 15 tick/s | 约 60 分钟 |
| 1920×1080 全屏 | **约 2.7 tick/s** | **约 5.5 小时** |

同一个探针、同一个场景，只换了显示档位，速率差 5.5 倍。这**与短采样基线矛盾**：`run_gpu_preview_frame_baseline.ps1 -Coupled` 在同样的 1080p 全屏档位下 600 帧只用约 5 秒（≈120 fps，墙钟 p50 6.6 ms）。差别在于那次只跑几秒就退出，而长稳跑几十分钟。最可能的原因是长跑中全屏窗口未被聚焦后受到节流，但本轮没有进一步区分（区分它需要在长时间里逐帧记录帧率并与窗口状态关联）。

**结论与取舍**：把「30 分钟 × 1080p」作为一个可在一轮内完成的门槛，在本机不现实（5.5 小时）。因此分工是：

- 1080p 的**帧时间**结论来自短采样基线（p99 30.285 ms、GPU p99 0.978 ms，见上）；
- 30 分钟的**稳定性**结论来自 720p 长跑（三场景全过）；
- 两者的**组合**（30 分钟持续 1080p p99）**未实测**，这是 T08 G06 明确留下的缺口，而不是被短采样替代。

## 性能回收：把脏块摘要移出 tick 关键路径

前面把瓶颈定位到了「每 tick 的异步往返」——GPU 渲染只占 p99 0.978 ms，但 77.8% 的帧在等 `tick_pending`，平均 4.69 帧才完成一个 tick。看代码就能看出原因：每个 tick 有**两次** GPU→CPU 异步往返。

1. `_start_tick` → `_render_begin_tick`（工具补丁 + 潮汐边界）→ 请求 **CFL tile** 回读
2. `_on_cfl_tiles` → `_render_finish_tick`（N 个子步）→ 请求 **dirty-max** 回读
3. `_record_dirty_max` → `_tick_finished` → `tick_pending = false`

关键观察：**dirty-max 摘要只喂碰撞代理**（决定哪些块要重刷），水面/沙物理一点都不读它。它却卡在 `tick_pending` 上，让每个 tick 都要等两次往返。而且它是个 atomic max 的纹理，语义上本来就是「最坏情况上界」。

改法：

- `_render_finish_tick` 在子步派发完就 `call_deferred("_tick_finished", ...)`，**不再等 dirty-max**。下一个 tick 可以在上一个摘要还在飞的时候就开始。
- 摘要仍在飞行时不重置 `dirty_max_texture`，于是那张纹理累积多个 tick 的 max；`dirty_ticks_covered` 记它覆盖了多少 tick，`_erosion_collision_chunks` 的每 tick 上界按它放大。**这是保守的**（宁可多刷碰撞块，不会漏）。
- `_record_dirty_max` 不再用 `tick_pending` 或 revision 相等做守卫——它描述的那一 tick 已经结束了，晚到依然有效。
- 当摘要被跳过（`ERR_UNAVAILABLE`）时计入 `dirty_summaries_missed`，便于核对「每个 tick 都被某个摘要覆盖」。

### 效果（1080p、全屏、关 VSync、耦合、600 帧）

| 指标 | 改前 | 改后 |
|---|---:|---:|
| 推进 tick 数 | 128 | 89 |
| 墙钟总计 | 4.95 s | 2.96 s |
| **等效 tick 速率** | 25.8 /s | **30.0 /s** |
| `tick_pending` 帧占比 | 77.8% | **18.8%** |
| 墙钟 p50 / p95 | 6.614 / 21.610 ms | **3.933 / 12.951 ms** |
| **墙钟 p99** | **30.285 ms** | **15.007 ms** |
| 墙钟 max | 58.492 ms | **18.711 ms** |

**p99 减半、max 降到三分之一，tick 速率正好到 30.0/s**——也就是冻结基线的 30 Hz。改动前后 600 帧推进的 tick 数变少，是因为帧变快了、同样的 600 帧覆盖的墙钟更短；按 tick/秒 比才是可比的。

### 同一个改动在 30 分钟长稳上的效果（1280×720）

短采样只说明一半，所以同一改动又跑了完整的 54000 tick（30.0 分钟）：

| 指标 | 改前（720p 长稳） | 改后（720p 长稳） |
|---|---:|---:|
| 帧数 / 每 tick 帧数 | 216031 / 4.0 | 108032 / **2.0** |
| 等效 tick 速率 | 约 15.6 /s | **约 31 /s** |
| 墙钟 p50 | 15.887 ms | 16.193 ms |
| 墙钟 p95 | 29.885 ms | 29.596 ms |
| **墙钟 p99** | **33.292 ms** | **33.959 ms** |
| 墙钟 max | 551.399 ms | **128.273 ms** |

**必须分开说清楚，不能只报短采样的数字：**

- **吞吐量翻倍**：每 tick 的帧数从 4.0 降到 2.0，tick 速率从约 15.6/s 到约 31/s，**达到了冻结基线的 30 Hz**。这是这次改动的主要收益。
- **尾部延迟基本没变**：p99 从 33.292 → 33.959 ms，仍然**略高于 33.3 ms 门槛**（高 1.9%）。原因也清楚——去掉的那次往返是**等待**，不是工作量；每个 tick 自己的耗时（剩下的一次往返加子步派发）没变，而 tick 帧占比从 1/4 升到 1/2，p99 落在 tick 帧上。唯一的尾部改善是 max 从 551 ms 降到 128 ms。
- 短采样里 p99「减半」是 1080p 全屏条件下的结果（那里帧率更高、tick 帧占比更低），**不能外推成 720p 长稳的结论**。报告先前只写了短采样那句，这里补齐 30 分钟口径。

所以这次改动**解决了吞吐**（单域到 30 Hz），**没有解决尾延迟**（p99 仍高 1.9%）。两条都要如实记。

回归：16 套全部通过。特别确认 `run_gpu_coupled_preview.ps1` 的数值**逐项不变**（collision_error 0.000872、dirty_summaries 150、dirty_bytes 38400）——那个探针逐 tick 同步驱动，两次往返之间没有重叠，所以走得还是「每 tick 一份摘要」的老路；这次优化只在生产那种 tick 背靠背的情况下生效。

## 未完成

1. **定位 SCN-03 的 8.6 MB 内存阶跃**：三场景长稳里唯一未解释的现象，已确认不可复现、且碰撞换块被定向探针排除，但成因仍未定位。
2. **G01 一致 tick 快照与版本迁移**：现有检查点回归覆盖了同格式存读与损坏文件拒绝（T04 跨进程检查点探针），但没有跨 `format_version` 的迁移测试；当前实现是「版本不匹配即拒绝」而非迁移，需要明确迁移策略或把它写成 ADR。
3. **G04 分块评估**：单域 25.8 tick/s 尚未达 30 Hz，按细则「单域性能达标后才评估」不启动。
4. **G06 收尾**：1080p 帧时间基线（p99 30.285 ms、GPU p99 0.978 ms）与无剪辑端到端演示都已出片；**30 分钟 × 1080p 的组合未实测**——实测该档位下长稳只有约 2.7 tick/s，一轮需要 5.5 小时，见上。

## 新风险

- 长稳探针的沙账本判据来自**回读累加**（float32 求和 + 影子账本），会随时间缓慢累积测量噪声：SCN-02 跑到 tick 8100 时该口径为 0.00106 m³ 且仍在增长。权威口径是 GPU 自身的沙审计（T04 耦合预览为 6.2e−7 m³），探针的 0.05 m³ 门只是粗网。报告不使用探针口径宣称守恒精度。
- 实时长跑受窗口可见性影响：隐藏窗口下 Godot 会降低更新频率，本轮 14–15.8 tick/s 是在编辑器同时打开的情况下测得的，不代表独占 GPU 时的上限。
- 长稳的墙钟成本很高（单场景 30 分钟模拟时间约需 65 分钟墙钟），因此长稳不是快速迭代的有效手段；回归用的短跑应当用固定帧率模式（`--write-movie` 或 `--fixed-fps`）解除实时约束。
