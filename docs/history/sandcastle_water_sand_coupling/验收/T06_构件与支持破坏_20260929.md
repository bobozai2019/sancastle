# T06 参数化构件与支持驱动破坏（2026-09-29）

状态：G01–G05 全部完成，NUM-10、NUM-11 已实测，64² 与 256² 主场景集成通过。仍未做：放置与工具桶的关系、写 `obstacle` 的构件、构件进存档（见「未完成」）。

## 目的与范围

`细则/T06_沙堡构件与局部坍塌.md` 要求参数化墙/塔/基座、状态驱动的支持图与损伤传播、破坏沙量可追踪的回收，以及几何/障碍/水/碰撞的事务一致性。

本轮实现的是**CPU 参考层的结构模型**：构件、支持图、损伤与破坏回收，加上 `契约/场景与自动验收契约.md` 的 NUM-10 三墙强度对照。GPU/画面集成与障碍—水重映射事务留作下一增量，原因见「未完成」。

## 设计决定

**构件是压实的沙，不是独立的实体。** ADR-002 把首版限制在高度图上，没有悬挑，所以墙/塔/基座表达为「在矩形足迹上抬高的一段沙」，并写入该区域的 `compaction`。这个选择带来两条直接好处：

1. **破坏回收是构造性守恒的。** 构件的沙本来就在高度场里，坍塌只需要把它的 `compaction` 降到松散值；随后 T05 的守恒坡面松弛把它塌成自然坡，沙总量不变。G03「破坏沙量可回收」因此不需要单独的回收路径，也不会出现「破坏时凭空生沙或吞沙」。
2. **不写障碍位，所以不触发水量重映射。** 细则禁止「只改障碍 mask 而不重映射水体积」；由于结构事件根本不改 `obstacle`，该禁令不被触发。真正需要障碍的事务（例如岩体、不透水构件）留给 G04 的下一增量。

**支持是纯局部状态量。** 一个足迹格的支撑来自它的邻居：同属本构件的格，或表面仍接近构件底面的床面。支撑比例 = 有支撑的邻居数 / 总数。损伤 `damage += (1 − 支撑比例) × 速率 × Δt / strength`，`strength` 复用 `sediment_step.glsl` 的同一条曲线（压实 0→1 使 0.7→1.8，湿度额外最多 ×1.25）。**没有任何固定倒计时**：完全有支撑的墙永远不累积损伤。

## G04 障碍—水重映射事务

细则禁止「只改障碍 mask 而不重映射水体积」。这条约束用**不变式**实现，而不是与上一帧 mask 做差分：`obstacle_remap.glsl` 的规则是「阻水格不得存水，它原本持有的水推到相邻畅通格」。因为是状态无关的，它对任何结构事件都幂等，也可以在什么都没变时无副作用地派发。

| 用例 | 场景 | 实测 |
|---|---|---|
| 阻断带 | 满水 64² 域中把一整列（64 格）设为阻水 | 水量 19.200000763 → 19.200000763 m³（不变）、阻水格残水 0.000000000 m³、悬沙 0.639999986 → 0.639999986 m³（不变）、128 个邻格收到水 |
| 封闭口袋 | 3×3 实心块，中心格四邻皆阻水 | 总量不变、外圈排空 0.000000000 m³、中心保留 0.300000 m（**未被吞掉**）、上报 1 个「受困」tile |
| 幂等 | 两条阻水列，连续派发两次 | 第二次最大逐格变化 0.000000000 m、上报 0 个变化 tile |

水与悬沙的共享边由两侧用同一份输入求值，所以总量按构造不变。动量不是契约的账本量，且阻水格没有一致流向，按显式选择置零（水面求解器对干格也这样做），畅通格自身动量不受影响。排不出去的口袋把负载保留在原格并通过 `remap_tiles` 的第 2 级标记上报，调用方必须计数，而不是当作已排出。

代码：`shaders/simulation/structures/obstacle_remap.glsl`、`obstacle_commit.glsl`、`scripts/structures/gpu_obstacle_remap.gd`；用例 `tests/structures/obstacle_remap_probe.gd`、`run_obstacle_remap.ps1`（64² 主 RD）。

## GPU 集成与「新流道进水」端到端

`tests/structures/structure_flow_probe.gd`（`run_structure_flow.ps1`）在 64² 主 RD 上把整条验收链跑一遍：建墙 → 挡水 → 掏空 → 坍塌 → 破口 → 进水。

**关键发现：竖直薄墙建不起来。** 1 格厚的 0.40 m 直立墙相邻落差 0.40 m，远超休止角（压实 0.9 时 `(0.674 + 0.3×0.9) × 0.125 = 0.118 m`），会被坡面松弛在第一步就推平。因此构件改为**沿足迹短轴线性收分的截头棱锥**（`height_at()` + `taper_slope_m`），落差落在休止角以内才能站住。这与真实沙堡一致：墙的稳定剖面本身就是收分的。

|---|---|---|
| 建墙 | 记账体积 / 格数 | 0.900000 m³ / 320 格 |

## 主场景（256² 预览）接线

`gpu_water_preview.gd` 新增 `enable_structures`（默认 **关闭**，以免扰动既有的耦合回归）与 `request_build_structure()`。一次构件事件在主场景里同时落三处：

1. 在 CPU 影子上栅格化构件（`field.add`）；
2. 用 `field.patch_for()` → `solver.dispatch_tool_patch()` 把抬高的沙与压实推到 GPU 沙层——**没有新的 GPU pass，也不写障碍位**；
3. 用 `collision_proxy.apply_shadow_chunks()` 刷新构件覆盖的碰撞块。

因此绘制网格（采样 GPU 沙层）、碰撞代理与求解器都来自同一个高度场。

## 不透水构件接入主场景

构件此前从不写 `obstacle`，所以 `obstacle_remap` 虽然通过了 64² 契约测试，却没有任何生产路径会调用它。现在补上 `blocks_water` 构件：

- `SandcastleStructure.blocks_water`（进存档）；`structure_field.obstacle_mask()` 给出整域的掩码，`has_impermeable()` 判断是否还有站立的阻水构件。
- 预览新增 `obstacle_remap`（仅当 `enable_structures`），并在构件建造时用 `_push_obstacles()` 走完整事务：`solver.update_obstacles(mask)` → `obstacle_remap.clear_tiles()` → `obstacle_remap.dispatch()`。
- 坍塌只会**打开**面积，不需要搬运水体积，所以只需更新掩码，求解器在下一个子步自己填回。

`tests/structures/impermeable_structure_probe.gd`（`run_impermeable.ps1`）在 256² 主场景上验证：

| 指标 | 实测 |
|---|---|
| 足迹格数 / 被标记阻水 | 200 / **200** |
| 阻水后水量审计 | 14.114071 → 14.663075 m³（期间潮位在涨）、负水 0、无效 0 |
| 坍塌后掩码残留格 | **0** |

**这份证据的边界**：探针只声明「掩码正确、没有负值/无效水、坍塌后掩码清零」；**水量守恒**这一条来自 64² 的 `obstacle_remap_probe`（阻断带 19.200000763 → 19.200000763 m³，逐位不变），因为在主场景里同步取「阻断前后」的水量需要一个与潮汐无关的口径。

调试这个探针本身花了几轮，原因值得记下来：**从主线程调用 `RenderingDevice.texture_get_data()` 会与渲染线程死锁**，而探针在派发 compute 之后再读回就正好踩上。最终改成只用预览自己异步发布的审计字段（`audit_water_m3`、`audit_negative_cells`），不再引入第二条回读路径。

## 构件进存档（后补）

冻结的存档 schema 里 `structures` 一栏写的是「拓扑、体积、损伤、支撑」，必需，但实现里从来没有写过它——检查点只带高度场，所以载入后的墙会变成一堆**没有支持图的惰性沙**，永远不会再塌。

现在补上：

- `SandcastleStructure.to_dict()/from_dict()` 与 `SandcastleStructureField.to_dict()/restore()`，序列化身份、足迹、剖面、损伤、建造压实度与已记账体积。沙本身仍走 `sand`/`compaction` 字段，构件层只带高度场表达不了的东西。
- 检查点采集写入 `structures` 与 `enable_structures`；`_ready` 在进入场景树**之前**读 `replay_checkpoint`（和真实载入同一时序），带构件层时自动把 `enable_structures` 打开。
- `checkpoint_store._validate` 新增 `invalid_structures` 分支，校验损伤 ∈ [0,1] 且有限、高度 ≥ 0 且有限，坏层和坏文件一样被拒。

## 主场景的支持驱动坍塌（后补）

演示录制时发现主场景里**墙建好却永不坍塌**：`gpu_water_preview.gd` 只调用 `structure_field.add()` 与 `patch_for()`，从未调用 `structure_field.step()`。也就是说主场景的构件只有几何与碰撞，没有支持模型。CPU 参考测试与 64² 端到端探针都自己驱动 `step()`，所以这个缺口只存在于主场景，测试矩阵没覆盖到。

已补 `_update_structures()`：每 tick 在无 tick 在飞行时用 `SIM_DELTA` 跑一次支持/损伤，坍塌后把松开压实的补丁推给 GPU。边界条件写在这里：支持度用 **CPU 影子**床面计算，影子在两次同步之间滞后，因此主场景的坍塌时机是 CPU 参考的**近似**而非同一数字。`tests/integration/record_full_demo.gd` 的演示里 1 个构件成功坍塌（`structures_collapsed=1`）。

## 放置工具与构件种类

`gpu_water_preview.gd` 增加面向玩家的放置路径：`place_structure_at_world(kind, world)` 负责世界→网格换算与足迹定位，`_place_structure_at_cursor()` 用 `_brush_hit()` 取光标世界点调用它。按 **B** 建墙、**N** 建塔（仅当 `enable_structures` 打开）。拆出 `place_structure_at_world` 是为了让放置数学可以不带鼠标地被测试驱动。

| 种类 | 收分轴 | 实测 |
|---|---|---|
| `WALL` | 仅短轴 | 9 格足迹中心 0.25 m、长轴保持等高 |
| `TOWER` | 两轴（金字塔） | 9×9 足迹中心 0.450000 m、角 0.010000 m（= 0.45 − 0.11×4）、偏轴 0.010000 m |

## 未完成

1. **与工具桶的关系。** 放置不消耗工具桶的沙，而是记入 `sand_source_m3`（外部源）。若要让玩家从桶里取沙筑堡，需要走 `place_sand` 路径并让桶成为约束。放置点也还没有体量/高度预览。
2. **写 `obstacle` 的生产构件。** 重映射 pass 已通过，但还没有任何生产构件会设置障碍位，所以它尚未接入预览的事件路径。塔/不透水墙属于这一类。
3. **塔与基座**只有枚举与足迹形状，尚未有各自的用例。
4. **「拍实加固」语义。** 强度用建造时的压实度（`_built_compaction`），所以用 `compact_sand` 工具加固既有墙不会延长它的寿命。若要支持，需要让工具同步更新这一记录。
5. **收分剖面是手填常量。** `taper_slope_m` 目前由调用方给定，没有从压实/湿度的休止角推导。若构件要由玩家用拍实强度决定高度，需要把它接上 T05 的休止角公式。
6. **构件未参与存档。** 检查点携带的是 `sand`/`compaction`，不含构件拓扑与损伤；载入后构件会作为普通沙存在（几何与碰撞正确，支持图丢失）。

## 新风险

- 强度用了构件的「建造压实度」而非实时压实度（`_built_compaction`），这样坍塌后的松散不会被强度曲线误读；但这也意味着用 `compact_sand` 工具加固既有墙不会延长它的寿命。若需要「拍实加固」，要让工具同时更新这一记录。
- 支持度量只看四邻居。形状很长的薄墙在中间被掏空时，支持比例的分辨率受格宽限制（每格 1/4）。已在用例中体现，但没有做形状敏感性研究。
