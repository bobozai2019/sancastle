日期：2026-10-10。结论：完成同一 test1 profile 的耦合场景、堆挖动作链与恢复继续演化验证；成本及长稳留待 G05。

## 场景与入口

`res://scenes/sandcastle_test1_beach_coupled.tscn` 继承现有 coupled v8 入口，使用与固定场景相同的 `implementation/test1_beach_v8_base.json`（SHA256 `b4c557c8d0c96fb8100bf1d0b64e3e32470659a1b5e7dcd090b13d7ed2136bca`）。相机、太阳、白沫及岸脚节点固化在场景；GPU 水沙、工具队列、侵蚀、碰撞代理及检查点继续由原入口管理。新脚本只配置视觉材质和 effective profile，不改源汇、沙量或动量计算。

## 动作链

运行 `godot.exe --path . --script res://task/sandcastle_test1_reverse_rebuild/implementation/probe_g04_edit.gd`。结果见 [manifest](g04_probe/manifest.json) 和同目录截图。工具库存初始为零，先挖取 0.050 m³；随后堆回 0.025 m³，再以 swept segment 挖沟 0.018 m³。场内沙量依次为 579.751160、579.701160、579.726160、579.708160 m³。沙量加工具库存前后相差约 4×10⁻¹⁰ m³，三个命令均进入已应用日志，碰撞代理有已应用 chunk。tick 180 有浪画面及检查点生成成功；恢复后的 tick=180、表现时钟=6.0 s、effective profile 一致。

恢复原场景和恢复场景随后**同帧成对推进**至 tick 210；rock、sand、water、两向动量、foam history、local front history 与工具库存 hash/值一致，逐项最大绝对差为零。独立检查点探针 [test1_pair_manifest](g04_probe/test1_pair_manifest.json) 在固定与耦合两场景的 tick 240 保存，并在 tick 240/270/600 检查 GPU 字段和画面 hash 一致，profile 及表现时间也一致。

曾将原场景和恢复场景分开顺序推进到 tick 210，得到少量浮点和局部浪前历史差异；恢复点 tick 180 原始字段完全一致。按项目现有成对同步验证方式复验后，所有字段逐值相同。这说明该顺序推进探针并非有效的确定性回归口径，失败结果保留在运行记录中，不将其回写为物理故障。耦合侵蚀会使初始高沙体在 tick 180 松弛成锥形；它仍来自可编辑权威沙字段。若以后要求保留高耸轮廓，需要单独按支持/材料契约论证，不能用视觉假体替代。

本目标未修改既有数值与碰撞实现。G05 将集中做三机位负例、代表性成本、旧回归与长稳。
