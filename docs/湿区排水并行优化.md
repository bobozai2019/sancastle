# 湿区排水并行优化（2026-10-18）

本次按用户要求实施第一版优化，已接入正式公共水响应。重点是先前约27ms的湿区排水；没有修改三工作槽、CPU回执消费时机、水tick顺序或碰撞更新策略。旧核作为数值参考和诊断对照保留，旧性能报告及失败记录不回写。

后续长时间铲动发现已保留的串行回退有严重成本：一行出现第9段湿区时，单次通用排水约200–210ms，合批会放大为秒级卡顿。首次失败的GPU原始输入已保存并复验，见[渐进卡顿定位](连续铲子渐进卡顿定位.md)。下述12ms改善只代表所测快速路径，不涵盖这类拓扑超限。

## 实现与数值边界

[water_response.gd](../scripts/simulation/unified_edit/water_response.gd)将原来单个工作组内的完整处理拆成拓扑与11个计算阶段：

| 阶段 | 工作分配 | 保留的约束 |
|---|---|---|
| 拓扑与CSR | 原64线程湿段图和行序压缩索引 | 原4邻接、每行8湿段、最多32分量；超限用原通用核 |
| 最大水面 | 每分量一组，组内并行最大值 | 双float水面比较，再加原0.02m容量上限 |
| 容量项、供体更新、接收格更新、审计项 | 各1024组×64线程 | 原逐格公式、携沙/动量比例和有限性检查 |
| 容量、实际搬运、残差、审计归约 | 每分量一组，最多32组 | 每个账目的逐格Kahan顺序不变；多个独立账目由不同线程同时累计 |
| 残差修正 | 分量内原行序 | 原ULP上限、容量夹取和停止阈值；到达停止条件后结束空扫描 |
| 全局回执 | 一组 | 原分量顺序；干格动量损失仍按分量/行序累计，仅在整数标记证明没有干格供体时跳过该扫描 |

[拓扑shader](../scripts/simulation/unified_edit/water_packed_topology.glsl)保留原湿段图构建过程；[分阶段shader](../scripts/simulation/unified_edit/water_packed_parallel.glsl)使用512格协作预取块，降低归约同步频率。计算阶段使用初始化时创建的11个特化pipeline，移除各阶段不需要的分支与资源使用；使用Godot的[计算pipeline特化接口](https://docs.godotengine.org/en/stable/classes/class_renderingdevice.html#class-renderingdevice-method-compute-pipeline-create)。

新增私有缓冲3,148,816字节（约3.003MiB），随Response分配/释放，不进入权威场或存档。阶段之间没有CPU读回或等待；仍由原共同决定控制沙、水、悬沙、动量的条件提交。非法输入、拓扑超限或快速候选审计失败后，原通用排水核重新计算原诊断，不掩盖拒绝。

没有改变沙水预算、浮点容差、分配语义、外部ABI和恢复规则。实际原生字节等价由下述独立对照验证，不仅依赖代码审阅。

## 最终性能对照

原始记录和来源归档：[证据目录](../test_output/packed_parallel_20261018/)，汇总见[comparison.json](../test_output/packed_parallel_20261018/comparison.json)。

- GTX1050、Godot4.7.2/D3D12 Forward+，真实主场景1280×720、VSync1、默认铲子，使用相同自动输入配方和初始脚印。
- 最终旧核/新核使用同一当前产品与探针来源。旧核仅由诊断装饰器替换packed实现；新核是正式默认路径。其余水阶段、槽位、碰撞、渲染不变。
- 浅水和干地各一组旧/新对照，每轮有160个水运行拖动帧和160个暂停水tick的拖动帧。GPU每帧最多采样首个水响应；最终对照不启用内部11阶段时间戳。

| 指标 | 旧核 | 新核 | 本次观测 |
|---|---:|---:|---|
| 浅水packed GPU中位数 | 27.26ms | **11.94ms** | 降低56.2%，约2.28倍 |
| 浅水packed GPU P95 | 27.66ms | 13.88ms | 降低约一半 |
| 浅水完整水响应GPU中位数 | 28.35ms | 12.98ms | 普通水tick未改 |
| 水运行时编辑批次GPU P95 | 118.56ms | **57.76ms** | 每批命令数受槽位和时序影响 |
| 水运行连续铲动帧时间P95 | 143.40ms | **66.26ms** | 降低53.8%；仍存在明显慢帧 |
| 同阶段最大帧时间 | 150.74ms | 76.04ms | 非消除卡顿 |
| 水暂停后铲湿沙帧时间P95 | 44.70ms | 29.25ms | 浅水编辑本身仍有成本 |
| 干地packed GPU中位数 | 1.99ms | 2.22ms | 增加约0.23ms空阶段开销 |
| 干地水运行铲动帧时间P95 | 22.67ms | 22.82ms | 本组整帧接近，不宣称零退化 |

浅水水运行阶段的帧时间P50为14.11→18.08ms，160帧总时长为6.75→4.36s。原分布混有大量短帧与长批次停顿，不能只看P50判断改善。CPU录制P50为2.19→2.22ms，额外阶段不是零CPU成本。

上述为相同配方下的实时操作对照；GPU变快会改变水tick与合批节奏，因此中间水场、批次数和采样数不完全相同。精确数值等价使用独立固定输入验证。每条件只做一次最终对照，不估计P99、不推广为所有硬件或稳定60FPS。用户编辑器保持开启，记录到的探针串行运行，不宣称独占GPU或已测得SM占用率。

## 后续：关闭连通排水时的独立初始化（2026-10-18）

按用户要求，策略2切换到独立[water_velocity_prepare.glsl](../scripts/simulation/unified_edit/water_velocity_prepare.glsl)，策略3仍走原packed/通用排水。原`water_displace_compensated.glsl`、拓扑、并行排水、公共速度/审计shader和速度归约shader的SHA256均与本轮修改前相同。该分支服务所有使用策略2的编辑命令，并非铲子私有实现；默认开关仍开启。

原策略2也要由单线程扫描全部65,536格，复制水状态、清理暂存和检查数据，之后才跳过连通分析。新核将这段拆为256组×256线程逐格处理，以及1组×256线程归约首个非法格并写回执。新增2KiB私有检查缓冲；两个阶段只在GPU上排序，没有新增CPU等待、权威写入、回执消费或碰撞策略。首个非法格仍按行序决定，保留有限值检查先于同格负值检查、忽略保留字段`flow.w`的原规则。开启连通排水时原8湿段/32分量快速边界和串行回退仍然存在；关闭分支不构建连通域，不受该边界影响。
