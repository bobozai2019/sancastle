# 连续铲子越挖越卡：湿区拓扑回退（2026-10-18）

本轮只增加诊断和复验，没有继续修改产品排水、批次、回执或碰撞实现。用户最新症状是“挖的时候越来越卡，松手恢复”，撤销此前“松手也持续卡”的描述。

## 已确认原因

**当前快速排水只支持每行最多8段湿区。铲动改变沙床与水深后，某行出现第9段，整域排水退出快速路径，改由一个GPU线程执行通用BFS和有序排水。** 多条这样的编辑命令又在同一批内依次执行，造成数百毫秒甚至秒级长帧。

这不是CPU与GPU逐阶段来回确认。水响应阶段之间没有CPU读回；CPU回执后移也不会消除这些GPU计算量。上一版并行优化覆盖快速路径，保留了原串行回退，因此没有解决此边界。普通水tick不执行该编辑排水核，松手、编辑批次排空后可以恢复流畅。

证据链（本项目实现的C3复现，不涉及竞品算法）：

1. [拓扑核](../scripts/simulation/unified_edit/water_packed_topology.glsl)按`water > 0.001`且`obstacle < 0.5`统计水平湿段；每行第9段令`bad=1`，返回时`receipt[27]`仍为0。
2. [公共响应](../scripts/simulation/unified_edit/water_response.gd)随后录制通用排水；[通用核](../shaders/simulation/edit_validation/water_displace_compensated.glsl)仅在`receipt[27]==1`时跳过，`local_size_x=1`，实际一个工作组。回退时会扫描整域并执行BFS。
3. 真实主场景持续铲动约43.58秒、响应序号1392时，GPU探针在通用排水之前保存了**当次原始输入**和快速路径回执。第166行（0基）有9段湿区，湿格44,137个，最大连通区44,111格，共5个连通区；21个湿格床面抬高。全部字段有限、深度与悬沙非负。回执27为0、间接dispatch为1。这次是每行容量超限，**不是32分量超限，也不是数值审计拒绝**。
4. 同一响应的通用排水GPU时间为209.664ms。随后稀疏采样共捕获17次慢回退，范围199.66–209.66ms。
5. 将这份输入单独交给旧核、新核及新核重复执行，完整四通道候选和128字节排水回执逐字节一致，16项检查通过；说明输入可复验，且这条回退路径原已存在。

原始证据在[本轮目录](../test_output/shovel_progressive_20261018/)。关键文件：[GPU原始输入](../test_output/shovel_progressive_20261018/witness_wet01.fallback.bin)、[拓扑复核](../test_output/shovel_progressive_20261018/witness_wet01.fallback.json)、[分时分析](../test_output/shovel_progressive_20261018/witness_wet01.progression.json)、[旧新核等价结果](../test_output/shovel_progressive_20261018/actual_pair/probe.json)。原始捕获SHA256：`9e3779949a6b33d96de5e90bde7c2fdd7ce9bc2318abade93100d103d6a66dbd`。

## 观测范围和排除项

Godot4.7.2、GTX1050、D3D12 Forward+、真实主场景1280×720、VSync1、默认铲子和运行中的水模拟。自动输入沿相邻8m轨迹连续移动，保持同一次手势，约60秒后松手，再运行水15秒、暂停5秒。每帧只采样首个水响应，不能把17次采样称作全部回退次数。

| 时间窗口 | 帧时间P95 | 观测 |
|---|---:|---|
| 铲动前 | 23.80ms | 水运行、无编辑 |
| 开始0–10秒 | 84.84ms | 已有合批卡顿；快速排水中位11.98ms |
| 30–40秒 | 105.08ms | 快速排水中位15.07ms |
| 50–60秒 | **830.09ms** | 反复出现约200ms的通用排水 |

| 暂停水 | 17.19ms | 无编辑 |

这轮`witness_wet01`来源检查通过，自动输入没有`no_active_stroke`拒绝，正常排空和释放。[witness_sources.zip](../test_output/shovel_progressive_20261018/witness_sources.zip)保存172份受测来源，[清单](../test_output/shovel_progressive_20261018/witness_sources_manifest.json)逐项匹配SHA256。探针增加两次私有GPU dispatch来保存首次失败输入，因此上述整帧数字属于诊断负载，不能作为无探针性能验收。

队列在各10秒窗口最多3–4项，没有随时间持续增长。单独的水tick约1.5–2ms，未出现同量级增长。CPU碰撞、录制和回执不足以解释约800ms长帧。静态内存包含累积的诊断记录，本轮不据此宣称产品泄漏或无泄漏。

更早的`sweep_wet01`没有原始输入捕获dispatch，已测到单次通用排水200.99ms、10条命令的编辑批次1786.73ms、最大帧1803.61ms。CPU该批录制6.44ms、回执验证2.31ms。这轮后半段出现`no_active_stroke`，与用户报告同期有手动操作，故只用作已发生慢回退的证据，**不能当作90秒不中断自动输入对照**，也不能精准归属到用户哪次手势。

其他记录保持原样：`long_wet01`是诊断脚本继承方法签名错误，未运行；`long_wet02`仅小范围来回挖，没有观测到通用回退，且运行中碰撞shader被其他工作修改，来源门不通过；`manual01`没有编辑enqueue或F8标记，碰撞脚本也有外部来源变化，**不能宣称已捕获用户那几次手动铲动**。用户随后确认手动复现但未按F8，此确认保留为症状反馈，不替代日志身份关联。

## 新增诊断和复验方法

[启动器](../tools/unified_edit_pipeline/run_shovel_trace.py)新增长时间轨迹与首次回退取证；只在诊断进程内装饰原有执行器，不修改产品入口。首次失败输入在GPU阶段边界保存，循环期间不增加CPU读回等待，结束后异步导出。

```powershell
# 纯手动：只在此新窗口操作。F8是可选标记，未按也会记录编辑开销。
python tools/unified_edit_pipeline/run_shovel_trace.py --long --manual --water-only --duration 120

# 自动连续扩大铲动区域，捕获第一次回退的原始输入。
python tools/unified_edit_pipeline/run_shovel_trace.py --long --sweep-area --wet --water-only --fallback-witness --duration 60

# 输入实际输出路径。所有运行应使用新输出文件名，避免覆盖历史证据。
python tools/unified_edit_pipeline/analyze_shovel_progression.py PATH/capture.json
python tools/unified_edit_pipeline/analyze_shovel_fallback.py PATH/capture.fallback.bin
```

手动采集若没有编辑命令，分析器会标为不足以定位编辑卡顿。长时间分析的CPU区间相交改用前缀和查询，保留嵌套区间口径；800组生成区间检查及100帧真实碰撞区间与原公式一致，减少日志分析本身的等待。

最终诊断脚本调整了初始化完成通知的顺序，并通过5秒铲动加松手/暂停尾段的短运行；无来源变化、排空/释放通过，未误报不存在的回退。Python编译、48处本地文档链接检查通过。工具来源归档见[diagnostics_final.json](../test_output/shovel_progressive_20261018/diagnostics_final.json)和同名zip；长时间定位数字仍对应前述`witness_sources.zip`，不混写版本。

## 修复方向（尚未实施）

优先消除“超过8湿段便退到单线程整域处理”的性能断崖：为任意碎片拓扑提供并行连通区与压缩索引，继续保留有序数值累计、原守恒预算与通用负例语义。仅把8调到更大的常数会移动边界，不能完整解决持续挖掘后的退化。

合批数量会放大单次200ms成本，可另行评估批次时间预算，但这属于调度缓解。应先用本轮真实9湿段输入，以及更多湿段/超过32分量的负例验证拓扑路径，再验证长时间可见场景；不能只重跑平整湿区的12ms用例。
