# 场景2性能分析

结论：当前场景2的主要压力是持续 MUSCL 模拟的 CPU 命令录制及 GPU 执行/同步。绘制本身也占用较多 GPU 时间；碰撞更新和空闲参数窗口不是本次首要卡点。上一轮录制缓存正在生效，本轮仅扩展采集工具，没有修改模拟或画面实现。

## 测量条件

- 正式入口：`res://scenes/playable/test1_geometry.tscn`，场景切换菜单中的第二项“test1 原比例沙滩 · 30×15”。
- Intel i5-9300H、NVIDIA GTX 1050、Godot 4.7.2 stable steam `ed1daf0bf`、D3D12 Forward+、可见窗口 1280×720、VSync 开启、无 FPS 上限。
- 使用直接启动的正式初始化、当前有效参数和默认相机；没有工具操作或手动造浪，参数窗口隐藏，参数服务正常运行。采集帧的窗口焦点比例均为 100%。
- MUSCL 默认算法、侵蚀/材料耦合、边界、局部浪前、白沫、植被等使用当前冻结配置。所有采集的配置完全相同，hash 为 `29f13acebadd886a2f04ec31cbb58c79ae643fc5ecf2003ffc9ff09883b9c8ae`。源码在各次采样内及最终核查时没有漂移。
- 初始化完成后预热 5 秒；各阶段再稳定 2 秒，正常模拟采集 20 秒、暂停采集 10 秒。依次运行四个独立进程；不并行压测。已有 Godot 编辑器保留，未锁定 GPU/CPU 时钟、功耗或排除所有桌面负载。

有效配置和所有资源指纹见 [effective_configuration.json](effective_configuration.json)，机位画面见 [scene.png](timing_off/scene.png)。MUSCL 脚本 hash 为 `1c924c4384a6a5726f4d58337a89af1796ddbadedd01ac28736e1bf97bf08adf`，与上一轮优化验收一致。

## 正常运行表现

以关闭 CPU 详细诊断及模拟 GPU 时间戳的 `timing_off` 为主要帧率结果。保留轻量逐帧记录和主视口绘制计时，因此也不是完全零采集开销。

| 条件 | 平均 FPS | 平均帧间隔 | P95 | P99 | 最大 |
|---|---:|---:|---:|---:|---:|
| 正常模拟 | 21.02 | 47.57 ms | 84.56 ms | 89.25 ms | 93.62 ms |
| 暂停模拟、继续绘制 | 60.02 | 16.66 ms | 17.10 ms | 17.34 ms | 17.82 ms |

正常段 421 帧中有 126 帧超过 50 ms，模拟时间推进为墙钟时间的 96.3%。80.5% 的采样帧三个工作槽都占满，67.0% 的帧有待录制 tick。暂停段没有新增 tick 或积压。

主视口 GPU 平均 11.89 ms，暂停时为 11.77 ms；正常段 CPU 视口提交约 0.37 ms。每帧约 67 draw calls、244 万 primitives。绘制已占据 60 FPS 的 16.67 ms 预算中的较大部分，留给持续计算的余量有限。当前 ReflectionViewport 测量值为零，没有据此套用主场景历史中的反射开销。

**采集扰动必须区分：** 同配置开启 CPU 时间线和模拟 GPU 时间戳时，本次为 14.36 FPS；附加稀疏 GPU 阶段标记时为 15.86 FPS；单独开启函数 Profiler 时为 21.38 FPS。详细计时会明显影响本次运行节奏，因此不能把前两者的 FPS 当作正常运行基线，也不能把其中的 GPU 区间精确外推为无计时状态的纯算子耗时。各次状态随时间推进，未将运行差异全部量化归因为某一个计时 API。

原始帧率数据：[timing_off/capture.json](timing_off/capture.json)、[summary.json](timing_off/summary.json)；各次配置与焦点核对：[validation.json](validation.json)。

## CPU 函数开销

使用 Godot 内置 servers/scripts Profiler，20.02 秒正常模拟期间记录 578 个 tick、428 帧。total 包含子调用，self 排除子调用；下列 total 不能相加。协程等待包装函数不作为热点。

| 函数/工作 | 调用数 | 累计 total | 累计 self | 解释 |
|---|---:|---:|---:|---|
| `water_muscl.record_tick` | 578 | 3353.57 ms | 1182.39 ms | 最大脚本热点，约 5.80 ms/tick，包含耦合和 RD API |
| `coupled.record` | 36992 | 1258.27 ms | 732.81 ms | 每 tick 固定调用 64 次，已包含在上一行 |
| `height.physics_consume` | 1202 | 330.76 ms | 34.88 ms | 碰撞结果应用；含 shape 更换 |
| `height_surface._replace_chunk_shape` | 1580 | 266.75 ms | 266.08 ms | 单块约 0.169 ms |
| `collision_prepare_job.decode_heights` | 1590 | 142.31 ms | 142.31 ms | 碰撞高度准备 |
| `parameter_service._process` | 428 | 35.45 ms | 8.94 ms | 约 0.083 ms/帧，远小于模拟录制 |
| `water_muscl._prepare_recording` | 578 | 1.54 ms | 1.54 ms | 缓存键检查；采样期间 append/建表函数均为 0 次调用 |

参数行 `refresh` 在正常和暂停阶段都是 0 次。证据支持“空闲时没有全量参数行刷新”，不外推到连续拖动参数的成本。

RD 原生 API 的逐帧累计中，`compute_list_end` 约 89.9 万次、494.47 ms；间接 dispatch 约 66.5 万次、232.47 ms。大量固定列表边界和绑定仍需每 tick 重新录制，缓存只消除了参数重建与查找。`call_on_render_thread` 的累计包含回调实际执行，不能当成单独等待时间再加到 MUSCL 上。

CPU 时间线另显示集中提交：在开启诊断的正常段，288 次 pump 中，144 次不提交、144 次一次提交 3 个 tick。最长三次 pump 为 38.66、31.74、31.47 ms，均含 3 次提交。这种批量补充工作会增加帧时间尖峰。该事实来自诊断运行，不能未经对照把相同毫秒值套到普通运行。

碰撞应用区间平均 1.15 ms、P95 1.99 ms、最大 2.16 ms；20 秒累计约 212 ms。它值得继续关注，但不能解释此次 50–90 ms 级常见长帧的全部成本。

原始数据：[functions/messages.json](functions/messages.json)、[functions/frames.json](functions/frames.json)；解码表：[functions/functions.csv](functions/functions.csv)、[functions/functions.json](functions/functions.json)；集中提交记录：[burst_analysis.json](burst_analysis.json)。

## GPU 区间定位

第一轮诊断的完整模拟 tick 区间平均 24.22 ms、P95 37.02 ms；完整批次平均 24.42 ms；发布区间约 0.136 ms。tick 与批次互相包含，不能相加。这些是 GPU 时间戳区间，不是无计时运行的固定成本，也不能直接当成纯 shader 忙碌时间。

进一步仅在采样工具内包装现有耦合/尾部回调，每 16 个 tick 标记一次，原回调参数、调用次数和位置保持不变。正常段得到 29 个完整样本，每个都包含 64 次耦合回调。

| 同一批 GPU 抽样 tick 内 | 平均区间 |
|---|---:|
| 整个 tick | 27.13 ms |
| 64 次水沙/材料耦合合计 | 2.95 ms |
| 植被、局部浪前、白沫、碎石等尾部更新合计 | 0.221 ms |
| 边界处理 | 0.044 ms |
| 剩余主流程区间 | 23.91 ms |

剩余区间约占 88%，包含 MUSCL 决策、空间算子、RK、归一化、验证、sim_finish 以及其间调度/同步和未细分间隙，不能直接称为某一个水 shader 的耗时。当前证据不支持优先优化新增边界或尾部消费者；植被的**绘制**仍包含在主视口成本里，本表没有单独测量它。

原始标记与分段样本：[gpu_detail/capture.json](gpu_detail/capture.json)、[gpu_detail/summary.json](gpu_detail/summary.json)。

## 优先级与可信度

1. **C3 观察 / C2 归因：** 正常模拟低帧率、暂停后约 60 FPS、持续槽占用，以及函数/GPU 两类证据共同支持优先处理 MUSCL 的命令录制和执行链。缓存已经生效，剩余问题不是每 tick 重建参数表。
2. **C3 观察 / C1 优化候选：** 三批集中录制造成 CPU 峰值；后续可验证分散提交或把固定录制路径移入更低开销的实现。需要检查吞吐和完成态契约，不能只限制提交次数就宣称优化成功。
3. **C3 观察 / C1 优化候选：** GPU 主流程余项最大，下一步应细分决定、边通量、RK、归一化及同步开销，再决定是否能减少冗余工作。保持 MUSCL、64 次稳定性尝试、守恒与可见效果；不通过改算法或降低精度掩盖开销。
4. **C3 观察：** 绘制约 12 ms 是第二项 GPU 压力；碰撞和参数 UI 的观测成本更小。未做逐绘制层隐藏对照，因此暂不指定某种材质或植被为绘制瓶颈。

适用范围仅为本机、固定机位、当前初态及无工具操作。未测场景切换耗时、运行中大量挖填、手动造浪峰值、其他相机角度和长时间运行；不将采样区间外的行为纳入结论。

## 验证与复验

四次场景均未报告模拟故障，来源配置和资源指纹一致，诊断缓冲没有丢弃事件。函数调试器原始消息包含 168 条启动脚本警告；退出时 GodotIQ 插件另输出 `Capture not registered: 'godotiq'`，发生在两段采样结束之后，原始日志保留，不将其算成模拟错误或计时热点。其他三次运行日志无 ERROR。

工具位于 `tools/parameter_windows/scene_profile.gd` 和 `function_profile.gd`，本目录 `tools/` 保存交付时版本。代码和小型配置快照见 [code-and-settings.zip](code-and-settings.zip)，不包含完整纹理/网格，不能作为独立可玩工程；完整来源 hash 保存在有效配置中。证据 hash 见 [evidence_manifest.json](evidence_manifest.json)，证据不依赖 `test_output/` 留存。
