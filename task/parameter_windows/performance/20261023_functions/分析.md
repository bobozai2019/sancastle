# 函数级 CPU 耗时采样

## 采样范围

Godot 4.7.2 stable Steam，自带远程调试器 `servers` 脚本 Profiler，开启 native call 跟踪，最多输出 16,384 个函数条目。接收器只监听 `127.0.0.1:16017`。正式主场景，可见 1280×720 窗口、D3D12 Forward+、GTX 1050、VSync 开启。MUSCL MC SSPRK2 求解器，固定默认机位，参数窗口隐藏，参数服务正常运行。

准备完成后预热 5 秒，采集正常模拟 20.065 秒（486 帧），暂停后再采集 10.031 秒（507 帧）。采集脚本未注入工具操作或修改参数；记录中有鼠标相关输入分发和少量预览请求，因此不能声称完全没有操作系统输入。游戏运行逻辑未改动。

测得正常模拟约 24.24 FPS，帧间隔 P95 66.39 ms；暂停约 50.58 FPS，P95 21.87 ms。函数计时增加调用级开销，本次与此前 GPU 时间戳采集不是相同状态的严格速度比较。

## 正常模拟的函数热点

以下为完整 20.065 秒采样区间的累计 CPU 时间。总耗时包含子调用，self 为引擎报告的自身耗时；不同函数尤其父子函数的总耗时不能直接相加。这些是函数执行耗时，不是纯粹的函数进入/返回指令成本。

| 函数 | 次数 | 总耗时 ms | self ms | 平均总耗时/次 |
|---|---:|---:|---:|---:|
| domain_runtime._process | 486 | 5024.68 | 1.63 | 10.34 ms |
| pipeline.pump | 486 | 5021.90 | 11.42 | 10.33 ms |
| pipeline._submit_render | 595 | 4767.63 | 5.45 | 8.01 ms |
| water_muscl.record_tick | 595 | 4579.73 | 287.58 | 7.70 ms |
| water_muscl._dispatch | 536095 | 1936.12 | 1064.09 | 3.61 μs |
| water_muscl._decide | 230265 | 1353.44 | 397.23 | 5.88 μs |
| coupled.record | 38080 | 1271.52 | 737.68 | 33.39 μs |
| floating_props_service._physics_process | 1204 | 655.69 | 41.90 | 0.545 ms |
| height.physics_consume | 1204 | 232.75 | 29.40 | 0.193 ms |
| height_surface._replace_chunk_shape | 1112 | 173.28 | 172.87 | 0.156 ms |
| height.maximum_bed | 381 | 162.24 | 133.15 | 0.426 ms |
| protocol.hash_valid | 7185 | 141.90 | 128.52 | 19.75 μs |
| parameter_service._process | 486 | 28.97 | 8.10 | 0.060 ms |

主调用链为 `domain_runtime._process → pipeline.pump → _submit_render → transport.submit → _record_work → water.record_tick → water_muscl.record_tick`。`_dispatch`、`_decide`、`coupled.record` 均在 tick 录制内部，数字存在嵌套。

每 tick 平均约 901 次 MUSCL `_dispatch`、387 次 `_decide`，恰有 64 次 `coupled.record`。与源码固定 64 候选子步的录制循环一致。CPU 每个 tick 约 7.70 ms，即使某些间接 dispatch 实际不执行网格，其录制循环和 API 调用仍然存在。

## 引擎 API 观察

native API 使用逐帧条目合计；不将最终 profile_total 中的 native 条目视作可靠的全区间计数。Godot 会整理原生调用条目，同一 API 的签名前缀脚本不代表唯一调用来源。

| API | 区间调用次数 | 累计 CPU ms |
|---|---:|---:|
| RenderingServer.call_on_render_thread | 1860 | 4845.50 |
| RenderingDevice.compute_list_end | 924212 | 520.06 |
| RenderingDevice.compute_list_dispatch_indirect | 683136 | 257.58 |
| RenderingDevice.compute_list_bind_compute_pipeline | 924212 | 175.51 |
| RenderingDevice.compute_list_bind_uniform_set | 1118123 | 160.99 |
| RenderingDevice.compute_list_set_push_constant | 727703 | 116.44 |
| RenderingDevice.compute_list_begin | 924212 | 108.80 |
| RenderingDevice.compute_list_dispatch | 241076 | 89.78 |

`call_on_render_thread` 时间覆盖实际回调执行，不能把 4.85 秒全解释为排队或等待，更不能再与 tick 录制时间相加。compute_list 计时为 CPU API 耗时，不能当作 GPU 算子耗时。

## 参数窗口与暂停对照

运行期参数服务 `_process` 累计 28.97 ms，约 1.44 ms/秒、0.060 ms/帧；暂停期累计 49.98 ms，约 4.98 ms/秒、0.099 ms/帧。参数行 `refresh` 在两个采样区间均无调用。这说明空闲时不存在持续的全部参数行广播刷新。

窗口位置轮询仍有优化空间，但本次实测其所在后台路径远小于模拟命令录制。不能将拖动参数时的全量刷新问题外推成不操作时的主要卡顿原因。

暂停后的主要脚本开销为浮动物体物理回调（10 秒累计 247.21 ms），反射相机更新约 48.54 ms。未发起新的 MUSCL tick。两阶段的 self 热点详见 functions.csv。

## 优化方向与边界

优先检查 MUSCL 64 候选子步的 CPU 命令录制、重复创建计算列表/绑定/决定和耦合录制。单次辅助函数通常只有微秒级，累计开销来自调用规模和实际工作，不能简单断言“函数多所以慢”，也不能盲目内联全部函数。

之后检查碰撞高度更新与道具采样/恢复路径。参数 UI 后台轮询可低风险清理，但预期无法单独解决当前严重卡顿。

本次只定位，不修改稳定性子步上限、求解器、守恒或调度契约。GPU 的内部算子分摊仍需另加阶段标记；函数 Profiler 无法量出任意 C++ 内部调用栈。协程跨 await 的 total 可包含等待，本报告排除了采集 run 协程等等待包装函数。messages.json 另记录 177 条启动脚本警告，未将其算成测量期函数热点或运行故障。
