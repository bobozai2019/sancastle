# 不操作时卡顿采样

## 条件与方法

Godot 4.7.2 stable Steam，NVIDIA GTX 1050，D3D12 Forward+，可见窗口 1280×720，VSync 开启，无帧率上限。加载正式 `scenes/main.tscn`，固定默认相机，所有参数窗口隐藏，无工具输入，无参数改值。当前求解器为 `muscl_mc_ssprk2_v1`，侵蚀开启。

使用 Godot 内置 Performance、视口 CPU/GPU 计时、RenderingDevice GPU 时间戳，以及现有统一流水线的可选 CPU 诊断事件。不是 Tracy 捕获，也不是逐 GDScript 函数的脚本 Profiler 结果。生产运行代码未修改。

启动后等待准备完成及 5 秒预热；四个阶段之间等待 2 秒，每阶段采样 12 秒。阶段按顺序推进同一场景，并非相同 tick 的严格重复实验。参数服务停用阶段仅 `set_process(false)`，停止后台轮询和定时刷新，参数值及窗口节点保持原状。暂停阶段停止发起模拟 tick，仍渲染场景。

复现命令（PowerShell）：

```powershell
& 'D:/game/steam/steamapps/common/Godot Engine/godot.windows.opt.tools.64.exe' --path 'D:/godot/project/sandcastle' --script res://tools/parameter_windows/idle_profile.gd -- --output=res://test_output/parameter_idle_profile/repeat
```

| 阶段 | 帧数 | 平均 FPS | 平均帧间隔 ms | P95 ms | 最大 ms | >50ms 帧数 |
|---|---:|---:|---:|---:|---:|---:|
| 正常模拟，参数服务运行 | 265 | 22.09 | 45.27 | 63.53 | 69.75 | 102 |
| 正常模拟，参数服务后台刷新停止 | 220 | 18.32 | 54.58 | 89.45 | 105.39 | 108 |
| 恢复参数服务后台刷新 | 312 | 25.90 | 38.61 | 76.52 | 95.83 | 53 |
| 暂停模拟，参数服务运行 | 673 | 55.95 | 17.87 | 18.72 | 99.03 | 3 |

主视口 GPU 平均为 14.14 / 14.22 / 14.12 / 14.79 ms；另一个视口为 2.29 / 2.32 / 2.30 / 2.32 ms，场景具有 960×540 的 ReflectionViewport。GPU 时间戳中的视口 ID 在本次进程内有效。

模拟 tick 的 GPU 区间 `sandcastle_async_water_tick`，三个运行阶段平均为 20.07 / 21.98 / 18.63 ms，P95 为 23.83 / 38.84 / 35.72 ms。该区间涵盖水求解及其耦合、尾部消费者，不能称为纯水算法耗时。完整批次区间均值为 20.27 / 22.18 / 18.83 ms；发布区间约 0.13 ms。完整批次与 tick 区间嵌套，不可相加。

CPU 诊断共 25,935 条事件，无容量丢弃。批次提交记录区间均值 5.53 ms、P95 7.95 ms、最大 19.59 ms；pump 区间均值 4.29 ms、P95 12.07 ms、最大 29.15 ms。两者均记录在引擎报告的线程 1，且存在嵌套/同线程立即执行，不能将均值相加。碰撞高度应用区间均值 0.90 ms、P95 1.46 ms、最大 2.93 ms；回执 receive 均值 0.16 ms。采样中的 TIME_PROCESS 是引擎监视值，更新频率不同于逐帧时钟，不据此分摊精确函数成本。

## 判断与限制

直接观察：不输入也明显低帧率；停止参数服务后台刷新后仍有严重卡顿；暂停模拟后绝大多数帧恢复到约 18 ms。三个运行阶段模拟工作常占满三个位于 GPU 的在途槽，并有待处理 tick。第一段接近 30 tick/s，后两段模拟时间推进落后墙钟时间。

交叉支持：本次严重卡顿主要与持续模拟工作及其 CPU 提交/GPU 成本有关，参数服务后台刷新不能解释全部现象。渲染本身也有约 14 ms 的主视口成本，GPU 留给持续计算的余量有限。不能从顺序阶段中计算参数服务的准确毫秒开销，更不能把关闭后变慢解释成参数服务有加速作用。

源码候选：`water_muscl.gd` 的每个 tick 固定录制 64 个候选子步，每步有多次决定、空间算子、RK、耦合及归一化提交。间接调度可以避免未使用子步的实际网格计算，但 CPU 仍遍历并录制对应调用。这是优先深入的 CPU 提交路径；尚未逐阶段测量，不能断言其中某个算子是唯一根因。不得直接降低稳定性子步上限作为优化。

后续优先拆分 MUSCL/RK、水沙耦合、植被等尾部消费者的 GPU 与提交时间，再针对实际热点优化。UI 空闲轮询和全量刷新仍可优化，但当前证据不支持把它们列为严重空闲卡顿的首要修复。

限制：只有一轮、固定机位、顺序状态推进；启用了采样与时间戳，有诊断开销；同机保留已有 Godot 编辑器，未测硬件占用和功耗状态；本次不保证其他后台任务完全隔离。暂停阶段仍有少量尖峰，尚未归因。功能结论不外推至其他场景、硬件或交互负载。
