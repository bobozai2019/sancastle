# 流水线功能验证计划

角色：validation_plan。日期：2026-10-17。状态：[已完成]。本文件定义验证，实际结果见验收/G0–G7。V01–V16均已核对；默认三入口、十轮/三分钟联合操作通过，身份与边界见[G7](验收/G7_功能交付.md)。

## 1. 验证边界

- 先编译与短运行，再对应负例与集成，最后集中连续操作。每次只重跑受影响项。
- GPU、渲染完成态和 Jolt 碰撞使用真实可见窗口；纯协议/队列测试可无窗口。记录实际引擎、后端、场景、资源和配置，不能用导入成功冒充 GPU 通过。
- 不设 FPS、吞吐、耗时、占用率、固定反馈帧数或质量闭合误差 KPI；不启动旧 300 秒配对成本/30 分钟性能 Gate。
- 超时只用于发现不终止、死锁或设备问题。记录 `incomplete/failed` 和队列状态，不能把超时解释成普通命令拒绝。
- 只跑当前工程的一份自有功能探针，不复制工程、不自动关闭其他开发进程。当前阶段不需要独占 GPU 性能环境。

## 3. 观测与判定方法

事件最少记录：`generation, frame_id, phase, batch_seq, command_id（必要时）, slot_id, lease_id, state_seq, snapshot_seq, chunk_ids, pending_count, in_flight_count, event`。事件包括 enqueue/submit/gpu_complete/cpu_consume/snapshot_capture/collision_apply/release/reject/error。记录有界，关闭测试观测后功能不能改变。

关键判据：

1. 用事件顺序证明 B 提交不依赖 A 的 CPU 消费，不能仅凭“函数叫 async”判断流水线已成立；此证据不等于测得硬件重叠时间。
2. 用最终 GPU 字段、局部变化和实际碰撞射线证明结果，不能只比较计数或脚本退出码。
3. 测试时可以读回全部相关字段在 RAM 中比较；产品正常路径不能依赖这种逐笔读回。全拒绝批次和混合批次分别验证。
4. 比较相同初始化/相同输入顺序的参考结果，不因新调度改变了模拟交错就强求整个旧运行逐位一致。必要的浮点误差先固定测试容差并解释；“账本允许近似”不能作为 NaN 或部分提交的豁免。
5. 验证碰撞最终收敛时先停止新输入及自动地形变化，并让已接纳任务收尾；持续变化期间只检查版本和数据正确性，不设固定滞后帧数。
6. 实时运行和模拟暂停模式分别覆盖，模拟暂停不等于 GPU 资源已经空闲。

## 5. 证据与磁盘控制

每次 run 保存一份小型 manifest（源码/场景/profile hash、引擎路径/版本/hash、后端、有效配置、命令）、结果 JSON、有界事件日志、runtime log 和退出/释放摘要。完整原始场只在必要失败时留小样本，优先 RAM 比较与 hash；快照格式用例只创建必需的临时样本，并记录按用途清理的路径。

机器输出：`test_output/gpu_pipeline/<unique_run>/`。Gate 摘要：本目录 `验收/G0_...md` 至 `G7_...md`。新计划证据独立保存，不混入准备关闭的旧线程计划。既有原始数据和失败结果不覆盖。报告分别写“通过/未通过/未执行/不适用”，缺失证据不能视为通过。

文档修改只检查链接、映射、状态和 diff，不为本次计划交付启动 Godot 或性能采集。
