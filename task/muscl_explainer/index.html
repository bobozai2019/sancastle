00 / 先建立地图

方程、算法、硬件，是三件不同的事

“用 MUSCL”与“每个格子计算浅水方程”可以同时成立。当前项目就是这样做的。

物理模型

浅水方程

规定水深和水平运动怎样变化。它把一根水柱沿深度概括成一份状态，适合描述摊在地面上的水和长波。

它不逐粒追踪水，也不能直接解析翻卷浪头、飞散水滴等完整三维运动。

数值方法

MUSCL + SSPRK2

MUSCL 改善“格子边上应该是什么状态”的估计；SSPRK2 改善“从现在走到下一刻”的计算。

当前还包含 Rusanov 通量、床面修正、湿干处理和防止负水深的限制。

执行硬件

CPU + GPU

CPU 安排计算顺序与资源，GPU 并行计算大量格子。这个项目的步长判断和试算接受／拒绝也在 GPU 上完成。

“GPU 在算”并不意味着 CPU 没有录制、提交和管理成本。

用课堂打比方：浅水方程是题目规则，MUSCL 是解题方法，GPU 是同时做很多份计算的学生，CPU 负责发题和安排顺序。

“浅”主要指水深相对水平变化尺度较小，不只是“水不到膝盖”。二维网格记录水平 X、Z 方向，水深是每格的一个数；画面上的三维水面由这些状态和渲染材质共同构成。浅水模型参考

01 / 从账本开始

先保证：左边少的水，右边确实收到了

当前沙盘的模拟区域是 32 × 32 米，划成 256 × 256 格。每格边长 0.125 米。你可以把它想成一排排没有隔板、能够相互交换水的小盒子。

每个格子记什么？

  • 床面 b：岩层加沙层的高度。
  • 水深 h：床面上有多厚的水。
  • 动量 q：与水深和速度共同有关，qx = h × u，qz = h × v。
  • 悬沙 s：水里带着的沙，另有湿度与压实度等材料状态。

为什么不是只记水位？

同样高的水面，可能有很深的坑，也可能只有薄薄一层水。水已经向右流时，还存在惯性。只知道水面高度，无法完整描述运动。

这里的 q 是省略常密度后的浅水动量变量，单位 m²/s，不是整个格子的 kg·m/s。干格和极薄水层有专门的速度处理。

实验 A：搬水，但不造水

守恒记账示意

两个格子面积相同，初始水深分别为 0.8 m、0.4 m。拖动滑块，指定从左边搬多少水到右边。

左格水量12.500 L
右格水量6.250 L
总水量保持18.750 L

这只演示同一份搬运量怎样同时记在两边；没有计算压力、惯性或真实流速，不是一个完整浅水求解器。

新水量 = 旧水量 + 流入 − 流出 + 外部加入 − 外部移除单格体积 V = h × Δx²。当前单格面积为 0.015625 m²；水深增加 1 米，对应水量增加 15.625 升。

相邻格子共用一条边。我们先算这条边通过多少水，再让一侧扣除、另一侧增加。这个“跨边搬运率”叫通量。如果一格只有半杯水，就不能让它流出一整杯；当前算法因此还有出流限制，保护水深不变成负数。

在封闭区域内，这种配对是守恒的基础。游戏还有边界供水、排水与数值修正，需要分别核对。守恒不等于所有场景总水量永远不变，而是变化应能解释、能对账。

实现依据：域坐标、单位与字段 · 出流限制 · 水与悬沙搬运

02 / 空间上的细致

MUSCL：每格一个平均数，还能推断什么？

假设三个相邻格子的平均水深依次是 0.2、0.4、0.6 米。只把中间一格看成平平的 0.4 米，会丢掉“水面正在向右升高”的信息。MUSCL 会参考邻格，给这一格估计一段坡度。

一阶方法把每格内部当作一个常数；MUSCL 重构允许每格内部是一小段倾斜直线。平均数仍然保留，但格子左边和右边可以给出更合适的状态，再据此计算边通量。

实验 B：同一组平均数，两种表达

一维重构示意 · 无时间推进
圆点：格子的平均值灰色横线：一阶蓝色线段：MUSCL

每条蓝线都穿过自己的平均值；它们不必在边界接上。边界两侧的不同估计，正是通量计算要处理的输入。此图只重构平床上的标量水深，省略二维流动、床面修正与干湿边界。

为什么还要加“限幅器”？

如果照着坡度大胆延伸，在波峰、陡坡或水边，可能猜出虚假的尖峰，甚至负水深。限幅器会在这些位置收敛一些。当前默认使用 MC；局部越不平滑，越可能退回更保守的估计。

MUSCL 的目的不是让水“更快扩散”。它主要提高空间估计的准确性，减少数值计算把波形过度抹平的现象。这里的“抹平”叫数值耗散，不等同于真实水的黏性。

它也不能保证所有波都保留：网格太粗、波太短，或者限幅与湿干保护介入，波仍然会衰减。

想看一点公式：怎样算出格内坡度？

先算左边差值 a = 本格平均值 − 左格平均值，右边差值 b = 右格平均值 − 本格平均值。如果 a、b 符号不同，说明可能到达了峰或谷，此处取零坡度。

MC(a,b) = sign(a) × min(2|a|, 2|b|, |a+b|/2)上式用于 a、b 同号；异号或含零时为 0。格子左右端值 = 平均值 ± 坡度/2。

当前保波参数在 MC 与 Superbee 坡度之间混合：坡度 = (1−r) × MC + r × Superbee。r 的范围是 0～1。增大它可能让某些轮廓更锐利，但并不保证任何场景的波幅、传播距离或性能都单调增加。

实现依据：重构与共享边通量 · MC、Superbee 与安全限制

03 / 时间上的细致

一次更新，并不是“算一遍所有格子”

现在我们能估计水往哪里走，但还要决定走多久。当前 CPU 每次请求推进 1/30 秒；GPU 会把这段时间拆成若干小步。每个小步又有两阶段试算、检查和水沙交换。

为什么会读邻格，但不会按屏幕顺序“一格接一格”推进？

一次派发的全部线程都读取同一份旧状态，把结果写入另一份纹理。比如 (3,2) 的线程即使先完成，也不会让 (4,2) 提前用到它的新水深。阶段之间再通过依赖与同步，让下一阶段看到完整结果。

因此点击一个像素只是放大观察，不是让那个像素先动。减少纹理复制或复用缓存时，必须保留这条读写规则，以及水、沙、动量和完成时间的一致性。

这 6 × 6 格到底算了什么，哪些没有算？

这里实际计算平床、全湿、封闭边界条件下的 MC 重构、Rusanov 通量、二维 CFL、两次供水限制与 Euler 更新、SSPRK2 合成，以及随水搬运的悬沙。边界使用墙面压力；有干格速度处理与速度上限。水包初态的中心有一小片悬沙，平静对照的悬沙为 0。

没有模拟变高低的床面、障碍物、边界造浪、侵蚀沉积、湿度压实、坡面沙流、故障审计或真实 GPU 调度；因此第 07 步明确显示“耦合关闭，状态不变”。不是把尚未实现的沙流画成计算结果。

当前预设每轮 4 ms 可用一个子步完成。页面同时检查第二阶段 CFL；若后续状态需要更小步长，就报告并停止本轮教学推进，不把未完成的时间冒充完成。需要拆步、重试的完整流程请结合第 04 章理解。

两次试算，为什么只推进一次小步的时间？

把一整份水状态叫作 U，把“计算当前变化率”的操作叫作 L。SSPRK2 的结构如下：

U₁ = U₀ + Δt × L(U₀)U₂ = U₁ + Δt × L(U₁)U新 = ½U₀ + ½U₂这是时间积分的骨架。项目在各阶段还有供水限制、速度限制、床面项和合法性检查。

两次计算是为了更准确地估计同一段 Δt 内的演变。最后要和起点取组合，所以接受后累计的是 Δt，不是 2Δt。可以理解为：先做预测，再用预测后的状态检查趋势，最后修正答案。

完成的水深和流速会被白沫、湿沙、碎石、植被和漂浮物读取。侵蚀与沉积则会反过来改变沙床，影响下一次水流。这也是为什么不能只替换一段水算法，就假定其他表现完全不变。

实现依据：计算阶段录制 · 水沙和材料耦合 · RK 合成

04 / 步子不能太大

水流越快，一秒钟反而要算更多次

想象相邻同学按顺序传递消息。如果一次时间跨度太长，消息本该已经越过好几个位置，你却只用邻座的旧信息算答案，就容易出错。显式网格算法因此需要限制时间步长，这类约束叫 CFL 条件。

水的信息传播速度不只取决于“水本身流得多快”。浅水重力波的速度还与水深有关，近似为 √(g × h)。所以深一些的静水，也可能需要更小的步长。

候选 Δt = min(剩余时间, 0.2 × Δx / (aₓ + a𝓏), 重试上限)Δx 是格子边长；aₓ、a𝓏 是当前各方向传播速度上界。当前实现用 GPU 归约获取它们，并在第一阶段后再次检查。两个方向的最大值不必来自同一格。

64 格表示试算容量，不是 64 帧。真实试算被拒绝也会占用一个槽。这里的数字只解释量级关系，不是场景 2 的性能预测。

两种“快”要分清：电脑把同样一秒水运动算得更快，是性能优化；让水在现实一秒内只演化半秒，是模拟变慢。后者不能算同等效果下的性能提升。

还有一个很实用的推论：固定区域内，如果格子边长减半，格子数约增至 4 倍，CFL 允许的步长又大约减半，基础格子更新工作可能接近 8 倍。它只是均匀条件下的工作量估算，不是 FPS 必然变成八分之一。

实现依据：GPU 步长与接受／拒绝决策 · 外层 1/30 秒请求

05 / 从方法到机器

耗时来自算数，也来自搬运和安排

给你一张卷子，算题需要时间；反复找资料、抄中间结果、等待上一组交卷，同样需要时间。GPU 计算也是如此。

工作主要在哪里当前项目中的具体例子
重构与通量计算GPU读取自己及邻格，估计面状态，计算流动、压力和传播速度。
全场扫描与归约GPU各工作组算局部最大速度，再合成全场上界，决定安全步长。
纹理读写与状态复制GPU / 显存阶段间读写中间结果；每个接受子步把多张状态图复制回固定槽位。
检查与同步GPU / 引擎必须等边通量可用，才能算出流限制；必须等试算检查完成，才能接受结果。
命令录制CPU / 引擎绑定计算程序和资源，发出 dispatch。即使某次间接派发不做格子工作，也仍有录制成本。
其他场景负载CPU + GPU画水面、沙面、反射和白沫，处理材料、浮物与交互。

为什么说“超过 1,500 个阶段”，却不是全做 1,500 次大计算？

标准 MUSCL 加水沙耦合路径，每个候选槽约录制 24 个阶段；64 个槽就是 1,536 个，另有初始化、收尾和表现消费者。这里混合了全场核、小控制核和间接派发。GPU 完成目标时间后，后面的无效槽会让大核工作组数为零；部分小核仍被调用。

“预留了命令”与“真正执行了多少格子计算”是两个统计口径。现在已经跳过无效槽的速度扫描；继续优化要找到剩下的真实成本，不能仅按命令数量判断。

06 / 尽量让答案不变

下一轮优化：少做重复劳动

优化的首要约束：架构稳定、系统完整。保留权威状态归属、资源生命周期、阶段同步、完成态发布、沙水耦合与恢复契约。任何省时方案都先过这些约束，再比较性能；不能用跳过系统或混读新旧状态换取帧率。

保留 MUSCL，不等于必须保留现在每一次读取、复制和 API 调用。公式可以一样，组织计算的方式可以更经济。

状态说明：无效归约跳过、线程内面状态复用、CPU 命令描述缓存及固定耦合展开已经实现。下面四项是从当前代码发现的候选方向，尚未实现，也没有新的实测收益。
候选 1 · GPU

邻格资料，能否大家共用一次？

现在怎样做

A 线程算 A 格时会读 B 格；B 线程算 B 格时又会读取、重构 B 格。上轮解决了线程内部的重复，线程之间仍可能重复。

准备怎样改

尝试让一组线程把附近数据共同读到共享缓存，或者先计算可复用的重构量，再让边通量读取。

像什么？

从“每个同学都去图书馆抄同一页”，变成“这组先取一份，大家查阅”。

为什么还要实测？

共享缓存占空间，等同组同学准备好也要同步。预计算还会多一次写入和读取，可能抵消收益。

保持公式与限幅条件；核对边缘、障碍、干湿区域和异常输入。共享缓存方法的通用依据见 NVIDIA 文档；文档中的 CUDA 案例不等于本项目 GLSL 的收益保证。

候选 2 · GPU

试算失败，是否必须从第一道题重做？

现在怎样做

第一阶段后的 CFL 检查可能拒绝当前步长，然后减半重试。此时原始水状态尚未接受改动，但下一次仍会重算初始状态的边通量。

准备怎样改

保留不依赖这次 Δt 的第一阶段结果；重算出流限制、更新量等确实依赖新 Δt 的部分。

像什么？

计算题最后一步不合格，前面的已知条件和一部分中间结果仍可使用。

为什么还要实测？

如果几乎没有拒绝，这项收益很小；若保存中间结果增加了常规路径成本，也可能得不偿失。必须先统计拒绝率。

当前有些阶段工作纹理会被下一阶段覆盖，不能直接假定它们还在；缓存身份、错误标志和审计语义也要保持正确。

候选 3 · GPU / 显存

两本账本，能否交换名字而不整本重抄？

现在怎样做

接受子步后，水深、动量、悬沙、沙和材料等字段会被复制回公共槽 0。大量格子反复执行同样的搬运。

准备怎样改

评估两组读写槽交替使用，或把部分复制并入已有写入阶段，减少专门的全场复制。

像什么？

新答案已经写在 B 本上，考虑下次直接用 B 本，而不是先把它抄回 A 本。

为什么改动更大？

水沙耦合、工具与发布流程目前有固定槽位假设。所有消费者必须读到正确的完整状态，不能混用新旧两本账。

目标可以是不改变公式，但涉及接口和资源绑定。还需遵守跨线程读写依赖，不能让一个线程覆盖另一线程尚未读取的旧值。

候选 4 · CPU / 引擎

发题更省事，学生仍做同样的题

现在怎样做

命令描述已缓存，但每 tick 仍逐条调用 RenderingDevice：开始列表、绑定、派发、结束列表。

准备怎样改

评估把合适的计算放进同一列表，保留必要同步；必要时用原生 C++ 录制器减少脚本调用成本。

像什么？

老师把一组有顺序的题一次安排好，减少每道题重新分发材料的过程。

为什么未必大幅提升 FPS？

它主要减少 CPU 组织成本，GPU 仍做相同计算。如果瓶颈在 GPU，整体收益就有限。

Godot 的计算列表支持多次 dispatch；本项目需要另行验证列表合并后的资源可见性和间接参数依赖。官方接口说明

按什么顺序做，才不会“忙了很久却没变快”？

先量出热点→只改一个因素→核对结果→看整场景收益
  1. 先测：把重构、阶段更新、复制、水沙耦合、控制核与 CPU 录制分开计时，同时记录接受和拒绝次数。详细标记用于诊断，正常帧率另测，避免计时本身干扰结论。
  2. 再选：若重构最重，优先候选 1；若重试占比高，验证候选 2；若复制或 CPU 占比更高，再调整顺序。目前没有足够细的新计时替它们确定收益排名。
  3. 查答案：相同初态、相同工具输入和相同模拟时间，对照水、沙、动量、账本与完成时钟。以保持结果为目标的改动，先争取逐字节一致；出现差异必须解释，不能只说“看着差不多”。
  4. 看体验：在场景 2 的真实可见窗口测平均帧间隔、P95/P99 长帧、实际模拟进度，并覆盖挖填、造浪和保存恢复。阶段耗时改善不自动代表整场景改善。
07 / 优化的边界

“算法还是 MUSCL”，也可能已经改变水的行为

做法为什么可能更快代价或前提
复用计算、减少复制、优化录制同样的答案少做重复工作。目标是保持结果；仍需检查算术次序、同步和状态一致性。
把 CFL 从 0.2 调大可能用更大步长，减少子步。改变稳定性余量与误差；必须重新验证湿干、高速和陡坡，不能视为无损开关。
降低网格分辨率格子更少，允许的步长也可能更大。小波、小坑和岸线细节变粗，工具和碰撞尺度也需要核对。
降低侵蚀／材料更新频率减少每个子步的耦合计算。改变水沙相互作用的时序；即使按秒换算速率，也不能保证结果相同。
限制速度、减少造浪强度传播速度上界降低时，子步可能减少。实际运动本身改变；效果与性能需要一起评价。
降低候选容量，或让模拟少推进录制或实际工作减少。可能更常算不完请求时间。即使画面 FPS 升高，也可能只是水运动变慢。
换成另一种水求解器每步结构可能更简单。波形、流速、侵蚀、浮物和恢复兼容性都要重新评估。

如果目标是“保留现在的水感”，先做第一行。如果目标变成“接受不同水感，换更高帧率”，再讨论后面的取舍。无论选哪条路，都需要把水量、沙量、时间和其他消费者一起核对。

对当前项目的建议：保留 MUSCL，先测清重构、重试与状态复制的比例，再验证执行层优化。当前证据支持“还有可研究的冗余”，还不足以承诺“继续优化就一定稳定 60 FPS”。
08 / 三道随堂题

不用背公式，能解释这三点就抓住了主线

1. MUSCL 和浅水方程是什么关系？

2. 预留 64 个候选槽意味着什么？

3. 只把 CPU 命令录制加快一倍，能承诺 FPS 翻倍吗？

学完这页，你可以这样描述当前方案：我们在 GPU 上用网格求解浅水方程，MUSCL 改善空间重构，SSPRK2 改善时间推进；安全检查与水沙耦合增加了成本。优化先从重复计算、搬运和录制入手。

09 / 回到实际项目

源码与延伸阅读

正文中的“当前实现”来自以下本地源码与规格；“历史测量”来自已有测试记录；“候选优化”属于工程分析。四个实验仅用于解释概念，不运行游戏，也不预测真实 FPS。纹理实验在浏览器中计算简化的二维浅水算例，数值不是游戏 GPU 回读。

  1. 当前技术规格：网格、字段单位、MUSCL、时钟、保波参数与已知限制。
  2. water_muscl.gd：64 次候选尝试、阶段顺序、缓存与 CPU 录制。
  3. muscl_spatial.glslinc 与 muscl_math.glslinc：重构、通量、限幅与安全规则。
  4. rk_decide.glsl、rk_finalize.glsl 与 rk_normalize.glsl：步长、重试、合成与状态复制。
  5. coupled.gd：悬沙、侵蚀／沉积与材料更新。
  6. 水传播执行优化结果：本文历史场景 2 数值的完整条件与限制。
  7. Clawpack：The shallow water equations：浅水模型及传播速度的进一步解释。
  8. Godot：RenderingDevice：GPU 命令录制、时间戳、计算列表与同步接口。
  9. NVIDIA：CUDA Best Practices Guide：理解缓存、访存和性能测量；这里只借鉴通用原理。
