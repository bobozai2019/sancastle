## 每个运行目录

- `manifest.json`：run_id、目的、版本身份、源码／资源／配置 SHA256、引擎与设备、后端、窗口、VSync、初态与输入序列、采样开关。
- `command.txt`、`run.log`、退出码：实际启动命令与进程完成状态；脚本输出 PASS 不替代退出码和数据校验。
- `capture.json` 或分开的帧、CPU、GPU、子步数据：原始采样及单位、完成态关联、丢样本和来源漂移信息。
- `comparison.json`：基线身份、候选身份、差异字段、成本指标、波动估计、收益结论与限制。
- 对需要复现的原型保存对应源码快照或完整可恢复 diff；失败记录保留原样，修复使用新 run_id。

架构证据可以写在对应候选报告中，无须新建庞大的独立文档体系。至少记录涉及模块／职责、字段写入者与资源所有者、同步依赖、创建到释放及异常／恢复路径、候选撤回方式、未解决问题和 GA 结论。发现职责穿透或链路缺失时直接判定不合入，不能用性能报告替代架构结论。

## 比较规则

1. 先满足执行计划 C0/GA，再判断数值与性能；架构存在未解决的正确性或生命周期问题时，不因逐字节一致或 FPS 提高而通过。诊断与正常性能数据分开，不合并不同配置／计时开关的 FPS。
2. 依据[执行计划](../执行计划.md) C3 保留样本身份；跨时钟相减、缺失配对和来源漂移不得进入归因统计。
3. 数值对照保留权威字段、原双槽、完成时间、账本及原审计语义；新增私有缓存另做有效性与失效验证。
4. 性能结果报告实际模拟进度。tick 数量不是完成秒数；合成高重试场景不能替代场景 2 的实际结果。
5. 临时产物先写 `test_output/muscl_performance_round2/<run_id>/`，交付前迁入本目录并更新索引。任何必要的唯一证据不能只留在可删除目录。

清理 `test_output/` 不得影响未来最终报告的可追溯性。此文件目前只是待执行证据要求，没有填写任何虚构测试结果。
